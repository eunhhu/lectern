> 등급: `careful` · 게이트: `unit` · 의존: `P1-05`, `P1-06` · 소유: `packages/harness/`

## 1. 목표

`structure`와 `extract`가 만든 모델 출력을 코드로 검증·조립한다. 출처 토큰을 실제 세그먼트 범위로 펼치고(없는 id 삭제), 인용이 전사와 맞는지 보고, 날짜를 파서로 확정하고, 개연성 없는 항목을 거르고, 실패분은 모델 수리를 한 번만 한다. 결과는 `DocumentBody`(블록 id, 휴식 `GapBlock` 포함), `VerifiedEvent[]`, `VerifiedActionItem[]`, `VerifyReport`, `partial`이다. 사용자가 보는 변화는 없다.

## 5. 단계

1. 타입(전부 `verify.ts`에서 export).
   ```ts
   export interface VerifyInput {
     template: LoadedTemplate; structure: TemplateOutput; extract: Partial<ExtractResult>;
     transcript: { segments: { idx: number; start_ms: number; end_ms: number; speaker: string | null; text: string }[];
                   gaps: { kind: GapKind; start_ms: number; end_ms: number }[] };
     recordedAtMs: number; recordedAtSource: "client" | "media" | "upload"; tz: string; language: string;
   }
   export const VerifyOutput = z.object({ body: DocumentBody, events: z.array(VerifiedEvent), action_items: z.array(VerifiedActionItem), report: VerifyReport, partial: z.boolean() });
   export interface RepairTarget { ref: string; kind: "block" | "event" | "action_item"; item: unknown; issues: string[] }
   export interface RepairFix { ref: string; block: TemplateBlock | null; event: ExtractedEvent | null; action_item: ExtractedActionItem | null }
   export type RepairFn = (targets: RepairTarget[]) => Promise<RepairFix[]>;
   export function verifyDocument(input: VerifyInput, repair: RepairFn | null): Promise<VerifyOutput>;
   export function verifyStage(llm: LlmProvider, routing: Routing): StageDefinition<VerifyInput, VerifyOutput>;
   ```
2. `verifyDocument` 순서(계약 §1.8 ①→⑦). `known` = 전사 세그먼트 idx 집합. 항목 참조 문자열(`ref`): 블록 `"<sectionKey>#<구조 출력 안 1부터 위치>"`, 일정 `"event:<i>"`, 할 일 `"action_item:<i>"`, 결정 `"decision:<i>"`, 용어 `"glossary:<i>"`(`i`는 입력 배열의 0부터 위치).
   - **① 스키마**: 블록마다 `TemplateBlock.safeParse`, 일정·할 일은 `ExtractedEvent`/`ExtractedActionItem`. 실패하면 수리 대상(`issues`에 zod 메시지 앞 200자).
   - **② 참조**: 토큰을 `expandSourceTokens(tokens, known)`로 펼친다. 없어진 id마다 보고서 `reasons`에 `"dropped_ref:#99"`(`dropped`의 값 그대로). 블록의 `sources`는 블록 토큰 ∪ (list면) 항목 토큰. list 항목의 출처가 0개면 그 항목을 지우고(`reasons: "item_dropped_no_source"`), 항목이 0개가 된 list는 출처 0개 블록과 같이 수리 대상. 블록·일정·할 일의 출처가 0개면 수리 대상. 결정·용어는 출처가 0개면 바로 탈락(수리 없음). `pdf_pages`는 P3 전까지 무시(버린다).
   - **⑥ 수리(한 번만)**: 수리 대상이 있고 `repair`가 있으면 `repair(targets)`를 **한 번** 부른다. 같은 `ref`의 fix가 있으면 항목을 바꾸고 ①②를 그 항목에만 다시 돈다. 아직 실패하거나 fix가 없거나 `repair`가 `null`이면 탈락(블록이면 `dropped_blocks += 1`, `outcome: "dropped"`, `reasons`에 이유). 호출했으면 `report.repaired = true`. 고쳐져서 통과한 항목은 `outcome: "fixed"`.
   - **③ 인용 일치**(일정·할 일, `quote`가 null이면 건너뜀): 비교 글 = 근거 세그먼트들의 `text`를 `idx` 순으로 잇고 앞뒤 세그먼트 1개씩(`known`에 있으면)을 더한 것. `lcsRatio(quote, text) = LCS길이 / quote길이`, 둘 다 `normalizeForMatch(...).chars`로 만든 글자 배열. `< 0.8`이면 플래그 `low_confidence`, 일정은 `confidence = min(confidence, 0.3)`. 버리지 않는다. `lcsRatio`는 export하고 O(n·m) 동적계획으로 쓴다.
   - **④ 날짜**(일정은 `raw_expression`, 할 일은 `due_raw`가 있을 때): `resolveKoreanDate(raw, { recordedAtMs, tz })`.
     - 파서 성공: `resolution = { method: "parser", rule }`. 시작 = 파서 `date`+`time`. 일정의 모델 `model_resolution.date`가 파서 `date`와 다르면(파서에 `time`이 있으면 모델 `time`도 비교) 플래그 `date_mismatch`, `confidence = min(confidence, 0.6)`. 파서가 `weekday_mismatch`를 달았으면 같은 플래그. `recordedAtSource === "upload"`면 플래그 `recorded_at_estimated`, `confidence = min(confidence, 0.6)`.
     - 파서 실패(`null`): 일정은 모델 값(`date`, `time`, `end_time`, `all_day`) 사용, `resolution = { method: "model", rule: null }`, 플래그 `needs_review`. 할 일은 `due_at = null`, 플래그 `needs_review`.
     - 시각 변환 `zonedTimeToMs(date, time | null, tz)`: 시각 없으면 그 지역 자정. 구현: `guess = Date.UTC(y, m-1, d, hh, mm)`; `ms = guess - tzOffsetMs(guess, tz)`; `ms = guess - tzOffsetMs(ms, tz)`(서머타임 재확인 1회). `tzOffsetMs(utcMs, tz)`는 `Intl.DateTimeFormat`(`hourCycle: "h23"`) 부분으로 지역 시각을 `Date.UTC`로 만든 값에서 `utcMs`(분 단위로 내림)를 뺀 값.
     - 일정: `all_day` = 시각 없음. 종일이면 `start_at` = 그 날 지역 자정, `end_at` = **다음 날** 지역 자정. 시각 있으면 `end_at` = 끝 시각이 있을 때만 그 ms, 없으면 `null`. `tz` = 입력 `tz`. 할 일 `due_at`: 시각 있으면 그 ms, 날짜만이면 그 날 지역 **23:59**.
   - **⑤ 개연성**: 일정이 `end_at < start_at`이면 탈락(`"end_before_start"`). 날짜가 기준일(`recordedAtMs`의 지역 날짜)보다 365일 넘게 미래면 탈락(`"too_far_future"`; 일정·할 일 모두). 같은 녹음 안 중복(일정: `normalizeForMatch(title).chars.join("")` + 날짜, 할 일: 글자 + `due` 날짜 또는 `""`)은 먼저 나온 것만 남기고 탈락(`"duplicate"`). 기준일보다 과거인 `deadline` 일정과 과거 `due_at` 할 일은 버리지 않고 플래그 `needs_review`(날짜 문자열 비교).
   - 탈락 항목도 보고서 `items`에 `outcome: "dropped"`와 이유로 남긴다. 통과한 항목은 `ok`(변경 있으면 `fixed`, `reasons`에 이유).
   - **조립**: 템플릿 `def.sections` 순서로 섹션을 만든다. 제목은 템플릿 `title`.
     - `fill: "structure"`: 구조 출력의 같은 `key` 블록을 영속 형태로 바꾼다(`pdf_pages` 제거, `sources`는 펼친 `SourceRef[]`, list 항목도 같음, 블록 `id` 부여).
     - `fill: "events"|"action_items"|"decisions"|"glossary"`: 남은 항목으로 `list` 블록 하나(`style: "bullet"`, `heading: null`)를 만든다. 항목 `text`: 일정 `"<title> (<YYYY-MM-DD>[ HH:MM])"`, 할 일 `"<text>"` + 담당자 있으면 `" — 담당: <owner>"` + `due_at` 있으면 `" (기한: <YYYY-MM-DD>)"`, 결정 `"<text>"`, 용어 `"<term>: <definition>"`. 항목 `sources` = 그 항목의 근거. 블록 `sources` = 항목 합집합(중복 제거).
     - 항목이 없는 **선택** 섹션은 body에서 뺀다. **필수** 섹션은 `blocks: []`로 두고 `partial = true`.
     - 블록 `id`는 완성된 문서에서 앞에서부터 `b1`, `b2`, …(휴식 블록 포함, 전체에서 유일).
     - **GapBlock**: `transcript.gaps`마다 `{ id, type: "gap", heading: null, kind, start_ms, end_ms, sources: [] }`를 넣는다. 대상 섹션 = key가 `topics`인 섹션, 없으면 템플릿의 첫 structure 섹션. 블록 시각 키 = 블록 `sources`의 가장 작은 `start_idx` 세그먼트의 `start_ms`. 휴식은 시각 키가 `gap.start_ms`보다 큰 **첫** 블록 앞에, 없으면 맨 끝에 넣는다(휴식끼리는 `start_ms` 순).
     - `VerifyOutput.parse`가 통과해야 한다(영속 블록은 `DocumentBlock`).
3. `verifyStage(llm, routing)`: `defineStage({ name: "verify", version: 1, output: VerifyOutput, memo: "shared", retry: { maxAttempts: 3, repairs: 0 }, key, run })`.
   - `key`: `inputs`: `sha256Hex(canonicalJson(structure))`, `sha256Hex(canonicalJson(extract))`, `sha256Hex(canonicalJson(transcript))`; `prompt: sha256Hex(NOTES_SYSTEM + "\u0000" + REPAIR_INSTRUCTION)`; `template: \`${id}@${version}:${hash}\``; `provider: llm.id`; `model: routing.repair.model`; `params: { maxOutputTokens: routing.repair.maxOutputTokens, recordedAtMs, recordedAtSource, tz, language, lcs: 0.8, minFuture: 365 }`.
   - `run`: `verifyDocument(input, repairFn)`. `repairFn(targets)`는 `await ctx.meter({ provider: llm.id, model: routing.repair.model }, () => llm.generate({ schema: RepairFixes, system: NOTES_SYSTEM, context: notesContext(segments), instruction: REPAIR_INSTRUCTION + "\n" + JSON.stringify(targets), model: routing.repair.model, maxOutputTokens: routing.repair.maxOutputTokens, signal: ctx.signal }))`의 `value.fixes`. `RepairFixes = z.object({ fixes: z.array(z.object({ ref: z.string(), block: TemplateBlock.nullable(), event: ExtractedEvent.nullable(), action_item: ExtractedActionItem.nullable() })) })`. `REPAIR_INSTRUCTION`(한국어): "아래 조각은 검증을 통과하지 못했다. 이유(issues)를 고쳐 같은 ref로 돌려준다. 출처는 전사의 #번호만 쓴다. 고칠 수 없으면 그 ref를 빼라."
   - 수리 호출이 `HarnessError` kind `output_validation`으로 실패하면 잡아서 `fixes = []`로 보고 계속한다(항목 탈락). 그 밖의 오류(`transient`, `config`, `budget`, `canceled`)는 그대로 던진다.
4. `src/index.ts`에 export를 더한다.

| repair is skipped when nothing to fix | 기본 구조 | `repair` 0회, `report.repaired === false` |

| gap after all blocks | gap `start_ms` 가 마지막 블록 시각보다 큼 | 맨 끝 |
| gap goes to the first structure section when there is no topics | `seminar` 템플릿 | gap이 `summary` 섹션에 들어감 |

| stage: no call when nothing to fix | 기본 입력 | `calls.length === 0`, `ai_call` 0행 |
| stage: invalid repair answer drops the item | 공급자가 `{}` 두 번 답함(스키마 위반) | 던지지 않고 블록 탈락, `report.repaired === true` |
| stage: memo hit | 같은 `run`으로 두 번 | 두 번째 `resumed === true` |
| result parses | 위 조립 테스트 결과 | `VerifyOutput.parse(result)` 통과, `NotesResult` 모양과 호환 |

## 10. 명세 작성자 메모

- 계약이 정하지 않아 명세 작성자가 정한 값: 날짜 불일치 시 신뢰도 상한 0.6, `recorded_at_estimated` 상한 0.6, 날짜만 있는 할 일 마감 23:59, 결정·용어는 수리 없이 탈락, 항목 문장 형식(`"제목 (YYYY-MM-DD HH:MM)"`, `담당:`, `기한:`), 블록 id `b<N>`, 선택 섹션이 비면 body에서 생략. 바꿀 점이 있으면 오케스트레이터가 정한다.
- 계약 §1.6 `flags`의 `date_mismatch`·`weekday_mismatch`는 domain `VerifyFlag`(`date_corrected` 등)에 없다. P1-03 메모와 같은 충돌이다. P1-11이 변환해야 한다.
- 수리 호출에는 전사 전체를 문맥으로 보낸다(모델이 `#번호`를 알려면 필요하다). 계약의 "해당 조각만"을 조각 JSON + 전사 접두부로 해석했고, `structure`와 같은 접두부라 공급자 캐시를 쓸 수 있다.
- `verify`를 단계(`stage_run`)로 만든 이유: 수리 호출을 `ai_call` 원장에 남기고 재개 때 메모로 건너뛰기 위해서다. `routing.repair`만 쓴다.
- 일정 `kind`가 `deadline`일 때만 "과거 마감" 플래그를 단다(과거에 있었던 회의를 말하는 일정을 오염시키지 않기 위한 해석).
