# P5-05 Sign in with Apple

> 등급: `careful` · 게이트: `full` · 의존: `P5-04` · 소유: `apps/server/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

로그인 화면의 "Apple로 계속하기"로 들어올 수 있다. 흐름과 계정 연결 규칙은 Google 로그인과 같다. 다른 점은 셋이다: client secret이 서버가 만드는 ES256 JWT이고, 콜백이 Apple에서 오는 `POST`(form_post)이고, 이메일이 Apple의 전달용 주소일 수 있다. `LECTERN_APPLE_LOGIN=0`이면 404, 키 파일이 없으면 501이다.

## 5. 단계

1. `apple/es256.ts`
   ```ts
   export async function importP8(pem: string): Promise<CryptoKey>     // PKCS#8 PEM ("-----BEGIN PRIVATE KEY-----") → ECDSA P-256 sign key
   export async function signEs256Jwt(key: CryptoKey, header: Record<string, unknown>, claims: Record<string, unknown>): Promise<string>   // base64url(header).base64url(claims).base64url(r‖s)
   ```
   `crypto.subtle.importKey("pkcs8", der, { name: "ECDSA", namedCurve: "P-256" }, false, ["sign"])`, 서명은 `{ name: "ECDSA", hash: "SHA-256" }`. 키 내용은 로그에 남기지 않는다.
2. `apple/signin.ts`
   ```ts
   export const APPLE_AUTH_URL = "https://appleid.apple.com/auth/authorize";
   export const APPLE_TOKEN_URL = "https://appleid.apple.com/auth/token";
   export const APPLE_JWKS_URL = "https://appleid.apple.com/auth/keys";
   export const APPLE_ISSUER = "https://appleid.apple.com";
   export function appleSigninConfig(): { clientId: string; teamId: string; keyId: string; keyFile: string } | null   // null when any value is missing or the file does not exist
   export async function appleClientSecret(now?: number): Promise<string>
   export function appleAuthorizationUrl(p: { clientId: string; redirectUri: string; state: string; nonce: string }): string
   export async function exchangeAppleCode(code: string, redirectUri: string): Promise<{ id_token: string }>
   ```
   - client secret: 헤더 `{ alg: "ES256", kid: keyId }`, 클레임 `{ iss: teamId, iat: now, exp: now + 300, aud: "https://appleid.apple.com", sub: clientId }`(초 단위). 요청마다 새로 만든다(5분짜리).
   - 인가 URL 파라미터: `client_id`, `redirect_uri`, `response_type=code`, `response_mode=form_post`, `scope=name email`, `state`, `nonce`.
   - 교환: `POST` form `client_id`, `client_secret`, `code`, `grant_type=authorization_code`, `redirect_uri`.
   - 리디렉션 URI: `` `${config().baseUrl}/api/v2/auth/apple/callback` ``.
3. `auth-apple.ts`
   - `GET /auth/apple/start?next=`: 플래그가 꺼지면 404. `appleSigninConfig()`가 `null`이면 `501 not_implemented`. state를 만들고(`purpose: "apple_login"`, `userId`는 로그인돼 있으면 그 id, `redirectAfter: safeNext(next)`), `nonce`는 state 값이다. `302`.
   - `POST /auth/apple/callback` (본문 `application/x-www-form-urlencoded`: `code`, `state`, 첫 로그인 때만 `user`(JSON 문자열, `name.firstName`·`name.lastName`), 실패 때 `error`)
     - 이 요청은 Apple 사이트에서 오는 교차 사이트 `POST`다. **세션 쿠키가 실리지 않으므로 쿠키로 사용자를 확인하지 않는다.** CSRF 방어는 `state`(한 번만 쓰이고 10분 안에 만료)다. `Origin` 헤더가 있으면 `https://appleid.apple.com`이어야 한다(다르면 실패).
     - `error`가 있거나 `consumeOAuthState(state, "apple_login")`이 `null`이면 `303 /app/login?error=oauth`.
     - `exchangeAppleCode` → `verifyJwt(id_token, { jwksUrl: APPLE_JWKS_URL, issuers: [APPLE_ISSUER], audience: clientId, nonce: state })`.
     - `email_verified`는 Apple이 문자열 `"true"`로 줄 수 있다. `true` 또는 `"true"`를 참으로 본다.
     - state에 `userId`가 있으면 연결 흐름이다: `linkIdentity(userId, …)` → `303 /app/settings?identity=linked#account`(`taken`이면 `?identity=taken`). 쿠키가 없으므로 state의 `userId`를 믿는다(state는 그 사용자가 로그인한 채로 만든 것이다).
     - 없으면 `completeOAuthLogin({ provider: "apple", subject: sub, email, emailVerified, displayName })`. `displayName`은 `user` 필드의 `lastName + firstName`(둘 다 없으면 생략). 성공이면 세션을 만들고 `Set-Cookie` + `303 <redirectAfter>`. 실패면 `303 /app/login?error=<코드>`.
     - 응답은 모두 `303`이다(`POST` 뒤 `GET`으로 가야 한다).
   - 전달용 주소(`@privaterelay.appleid.com`)도 그대로 `email`로 쓴다. 기존 계정과 이메일이 달라 새 계정이 생기는 것은 정상이다.
4. `index.ts`: `v2.all("*")` 앞에 `v2.get("/auth/apple/start", …)`, `v2.post("/auth/apple/callback", …)`. v2 앱에 쿠키 인증 `POST`의 출처 검사(CSRF 미들웨어)가 있으면 이 경로는 그 검사에서 빼고, 뺀 이유를 주석으로 적는다(`// cross-site form_post from appleid.apple.com; protected by the single-use state`).
5. `test/fakes/apple.ts`
   ```ts
   export interface FakeApple { install(): void; restore(): void; requests: { url: string; form?: Record<string, string> }[];
     issueCode(code: string, idToken: { sub: string; email?: string; email_verified?: boolean | string; aud?: string; nonce?: string; exp?: number }): void;
     lastClientSecret(): string | null; publicJwk: JsonWebKey }
   export function createFakeApple(): FakeApple
   ```
   ES256(P-256) 키 쌍을 만들어 `APPLE_JWKS_URL`에 공개 JWK를 답하고 `id_token`을 서명한다. `appleid.apple.com` 밖의 호스트 요청은 던진다. 다른 가짜(`createFakeGoogle`)와 함께 설치할 일은 없다.
6. 테스트용 `.p8`: 테스트가 `crypto.subtle.generateKey`로 P-256 키를 만들고 PKCS#8 PEM으로 임시 디렉터리에 써서 `APPLE_SIGNIN_PRIVATE_KEY_FILE`로 준다. **저장소에 키 파일을 넣지 않는다.**

## 6. 테스트

`apple-es256.test.ts`: "signs a JWT that verifies with the public key", "header and claims round trip", "rejects a non-EC key file".

| 테스트 이름 | 준비 | 기대 |
|---|---|---|

| "new user via form_post" | `POST` 콜백(쿠키 없음) | 303 `/app`, `Set-Cookie`, 사용자와 identity 생성 |
| "name from the first login" | `user={"name":{"firstName":"선우","lastName":"김"}}` | 표시 이름 `김선우` |
| "private relay address" | `email: "abc@privaterelay.appleid.com"` | 그 주소로 새 사용자 |
| "email_verified as a string" | `"true"` → 성공, `"false"` → `error=email_unverified` | 그대로 |
| "nonce mismatch" | 다른 `nonce` | `error=oauth` |
| "state replay" | 두 번 | 두 번째 `error=oauth` |
| "wrong Origin" | `Origin: https://evil.example` | `error=oauth` |
| "link flow without a cookie" | 로그인한 채 start, 쿠키 없이 콜백 | `identity=linked`, identity가 그 사용자에 |
| "key file missing" | 파일 경로를 없는 곳으로 | start 501 |
| "flag off" | `LECTERN_APPLE_LOGIN=0` | 404 |

## 8. 하지 않는 것

- 네이티브 앱의 Apple 로그인(앱이 받은 identity token을 서버가 검증하는 흐름)은 만들지 않는다.

## 10. 명세 작성자 메모

- CATALOG는 "`SameSite=Lax` 세션 쿠키와 `state`로 확인"이라고 했다. Lax 쿠키는 교차 사이트 `POST`에 실리지 않으므로 실제로 기댈 수 있는 것은 `state`뿐이다. 이 명세는 그렇게 적었다(CONTRACTS 보충 절).
- App Store에 앱을 올릴 때 Apple은 계정 삭제 시 토큰 폐기(`/auth/revoke`)를 요구한다. 이 작업은 refresh token을 저장하지 않으므로 폐기 호출이 없다. 앱 심사 전에 사용자가 결정할 일이다.
