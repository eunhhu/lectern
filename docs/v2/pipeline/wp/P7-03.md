# P7-03 성능 예산

> 등급: `careful` · 게이트: `full` · 의존: `P3-10`, `P2-09` · 소유: `apps/web/`, `scripts/bench/`, `.github/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

성능이 조용히 나빠지지 않게 세 가지 수치를 CI의 `web` 작업에서 검사한다: ① 웹 초기 JS의 gzip 크기, ② 긴 전사(수천 구간)를 스크롤할 때의 프레임 시간과 화면에 그려진 항목 수, ③ 합성 1,000건에서 검색 p95. 예산은 첫 측정값의 1.2배이고, 수치와 근거를 `apps/web/README.md`에 적는다. 예산을 넘으면 CI가 실패한다.

기계에 따라 달라지는 수치(프레임 시간, 검색 p95)는 **CI에서 잰 값으로 보정된 뒤에만** 실패 조건이 된다. 그 전에는 측정값을 보고만 한다(5절 "보정").

## 5. 단계

1. `apps/web/scripts/budget.ts`
   ```ts
   export interface SizeReport { initial_js_gzip_bytes: number; total_js_gzip_bytes: number; css_gzip_bytes: number; initial_files: string[] }
   /** Entry scripts named in index.html plus every chunk they import statically, transitively. Dynamic import() is not followed. */
   export function initialScripts(distDir: string): string[]
   export function staticImports(source: string): string[]          // specifiers of `import … from "./x.js"`, `import "./x.js"`, `export … from "./x.js"`
   export function measure(distDir: string): SizeReport
   export function check(report: SizeReport, budget: { initial_js_gzip_bytes: number }): string[]   // problems; [] when within budget
   ```
   - `initialScripts`: `dist/index.html`에서 `<script … src="/app/assets/<파일>">`의 파일을 찾고(정규식으로 `src` 속성만 읽는다), 그 파일들의 `staticImports`를 따라가 닫힌 집합을 만든다. 상대 경로(`./`)만 따라간다. 같은 파일을 두 번 세지 않는다.
   - `staticImports`: 압축된 출력도 읽는다(`import{a as b}from"./chunk-1.js";`, `import"./chunk-2.js";`, `export{x}from"./chunk-3.js"`). `import("./lazy.js")`(괄호가 바로 오는 동적 import)는 **포함하지 않는다.**
   - gzip: `Bun.gzipSync(bytes, { level: 9 }).byteLength`.
   - 명령: `bun apps/web/scripts/budget.ts`(측정 JSON 출력), `--check`(`perf-budget.json`과 비교. 넘으면 `budget: initial JS <n> bytes (gzip) exceeds <limit>`을 stderr에 내고 종료 코드 1), `--write`(측정값 × 1.2를 올림해 `perf-budget.json`의 `initial_js_gzip_bytes`와 `measured`를 갱신). `dist`가 없으면 `budget: run "bun run web:build" first`와 종료 코드 2.
2. `apps/web/perf-budget.json`
   ```json
   {
     "initial_js_gzip_bytes": 0,
     "transcript_scroll": { "max_rendered_items": 0, "p95_frame_ms": 0, "max_long_frames": 0, "timing_calibrated_on": "local" },
     "measured": { "date": "", "initial_js_gzip_bytes": 0, "max_rendered_items": 0, "p95_frame_ms": 0, "long_frames": 0 }
   }
   ```
   `0`은 자리 표시다. 8단계에서 실제 값으로 채운다. `0`이 남아 있으면 검사는 실패한다(예산이 없는 것을 통과로 보지 않는다).
3. `apps/web/e2e/perf.e2e.ts`(fixture 프로젝트. `./fixtures.ts`의 `test`를 쓴다)
   - `test.describe.configure({ mode: "serial" })`, 테스트 하나: `transcript scroll stays within the budget`.
   - `/app/recordings/rec_os07`을 열고 `getByRole("list", { name: /전사/ })`의 첫 항목이 보일 때까지 기다린다.
   - 프레임 기록을 시작한다(`page.evaluate`): `requestAnimationFrame` 콜백마다 직전 프레임과의 간격(ms)을 `window.__frames`에 넣는다.
   - 목록 위에 마우스를 두고 `page.mouse.wheel(0, 900)`을 120번, 사이에 `waitForTimeout(16)`. 10번마다 `list.getByRole("listitem").count()`를 읽어 최댓값을 기억한다.
   - 기록을 멈추고 간격 배열을 가져온다. 계산: `p95_frame_ms`(가장 가까운 순위), `long_frames`(50 ms 초과 수), `max_rendered_items`.
   - 같은 과정을 **3번** 하고(매번 페이지를 새로 연다) `p95_frame_ms`와 `long_frames`는 세 번 중 가장 작은 값을 쓴다(잡음 줄이기). `max_rendered_items`는 가장 큰 값.
   - 단언
     - 스크롤이 실제로 움직였다: 마지막에 보이는 첫 항목의 `aria-posinset`이 처음보다 크다.
     - `max_rendered_items <= budget.transcript_scroll.max_rendered_items` — **항상** 검사한다(기계와 무관하다).
     - `p95_frame_ms <= budget…p95_frame_ms`와 `long_frames <= budget…max_long_frames` — `process.env.CI`이고 `timing_calibrated_on === "ci"`일 때만 검사한다. 그 밖에는 `test.info().annotations.push({ type: "perf", description: … })`로 값만 남긴다.
   - 측정값을 `test-results/perf/transcript-scroll.json`에 쓰고 `testInfo.attach`로도 붙인다. `PERF_WRITE=1`이면 측정값 × 1.2(시간은 소수 첫째 자리 올림, 개수는 올림 후 최소 +2)를 `perf-budget.json`에 쓴다.
   - 이 테스트는 `test.setTimeout(120_000)`.
4. `scripts/bench/budget.json`
   ```json
   { "recordings": 1000, "queries": 200, "search_p95_ms": 0, "calibrated_on": "local", "measured": { "date": "", "p95_ms": 0 } }
   ```
5. `scripts/bench/check.ts`
   ```ts
   export function decide(measured: { p95_ms: number }, budget: { search_p95_ms: number; calibrated_on: string }, ci: boolean): { enforce: boolean; ok: boolean; message: string }
   ```
   - `bun scripts/bench/search.ts --recordings <n> --queries <n>`을 자식 프로세스로 돌리고 stdout의 JSON을 읽는다.
   - `enforce` = `ci && calibrated_on === "ci"`. 강제일 때 `p95_ms > search_p95_ms`면 종료 코드 1.
   - 강제가 아닐 때는 종료 코드 0이고, CI면 `::warning title=search p95 not enforced::measured <x>ms (budget <y>ms, calibrated on <z>)` 한 줄을 낸다.
   - `search_p95_ms`가 0이면 종료 코드 1(`bench: no budget set`).
   - `--write`: 측정값 × 1.2(올림)를 `budget.json`에 쓴다. `--calibrated-on ci|local`로 표시를 바꾼다.
   - 측정 JSON은 항상 stdout에 그대로 낸다.
6. `.github/workflows/ci-cd.yml` — `web` 작업의 `Build and run Playwright + axe` 단계 **바로 뒤**, 보고서 업로드 단계 앞에 두 단계를 넣는다. 다른 줄은 바꾸지 않는다.
   ```yaml
         - name: Performance budget (initial JS size)
           run: bun apps/web/scripts/budget.ts --check
         - name: Performance budget (search p95, synthetic 1,000 recordings)
           timeout-minutes: 15
           run: bun scripts/bench/check.ts
   ```
   - 전사 스크롤 검사는 `perf.e2e.ts`가 `bun run web:e2e` 안에서 돈다(단계를 더하지 않는다).
   - `deploy-server`의 `needs`는 그대로다. `web` 작업이 빨개져도 서버 배포를 막지 않는다(지금도 그렇다).
   - 실패 시 올리는 보고서 경로(`apps/web/test-results`)에 `perf/`가 이미 포함된다.
7. `scripts/bench/README.md`에 `check.ts` 절(명령, 예산 파일, 보정 규칙)을 더한다.
8. **첫 측정과 예산 정하기**(로컬에서)
   1. `bun run web:build && bun apps/web/scripts/budget.ts --write`
   2. `cd apps/web && PERF_WRITE=1 bunx playwright test e2e/perf.e2e.ts --project fixture`(fixture 빌드가 필요하면 `bun run web:e2e`가 하는 빌드 두 줄을 먼저 돌린다)
   3. `bun scripts/bench/check.ts --write --calibrated-on local`
   4. 세 파일의 값을 확인한다. `timing_calibrated_on`과 `calibrated_on`은 `"local"`로 둔다.
9. `apps/web/README.md`에 `## 성능 예산` 절(테스트 절 뒤). 내용:
   - 표: 항목 / 첫 측정값(날짜, 어디서) / 예산(× 1.2) / 검사하는 곳 / 강제 여부
     | 항목 | 검사 |
     |---|---|
     | 초기 JS(gzip) | `apps/web/scripts/budget.ts --check`, CI `web` — 항상 강제 |
     | 전사 스크롤: 그려진 항목 수 | `e2e/perf.e2e.ts` — 항상 강제 |
     | 전사 스크롤: p95 프레임 시간, 50 ms 넘는 프레임 수 | `e2e/perf.e2e.ts` — CI 보정 뒤 강제 |
     | 검색 p95(합성 1,000건) | `scripts/bench/check.ts`, CI `web` — CI 보정 뒤 강제 |
   - "초기 JS"의 정의(index.html이 부르는 스크립트와 정적 import로 따라가는 청크. 동적 import는 뺀다).
   - 보정 절차: 이 변경이 들어간 첫 CI 실행의 로그에서 측정값을 읽는다 → `PERF_WRITE`·`--write`와 같은 규칙(× 1.2)으로 두 예산 파일의 시간 값을 고치고 표시를 `"ci"`로 바꾸는 PR을 낸다.
   - 예산을 올리는 규칙: 예산 파일을 고치는 PR은 이유(무엇이 늘었고 왜 필요한지)를 설명에 적는다. 측정이 흔들려서 올리는 것은 안 된다(측정 방법을 고친다).
   - 로드맵의 기준(검색 p95 200 ms, 전사 60 fps)은 Raspberry Pi와 실제 기기 기준이고, 여기의 수치는 회귀를 잡는 용도라는 설명.

## 10. 명세 작성자 메모

- D-P7-2는 "첫 측정값의 1.2배"라고만 한다. 시간 수치는 재는 기계에 따라 달라서, 로컬에서 잰 값으로 CI를 막으면 거짓 실패가 난다. 그래서 "CI에서 보정된 뒤에만 강제"라는 규칙을 더했다(CONTRACTS 보충 절). 보정 PR은 사람이나 오케스트레이터가 첫 CI 실행을 본 뒤 낸다(STATUS "실측 필요").
- D-P7-2의 "3,000구간"은 픽스처 `rec_os07`(수천 구간, 약 2시간 48분)로 본다. 정확한 구간 수는 확인하지 않았다. 3,000보다 적으면 README의 표에 실제 수를 적는다(픽스처를 늘리지 않는다 — 다른 e2e가 그 내용에 기대고 있다).
- CI에서 합성 1,000건 색인이 몇 분 걸릴 수 있다. 15분을 넘기면 `budget.json`의 `recordings`를 줄이고 README에 이유를 적는다.
- 프레임 측정은 헤드리스 Chromium의 `requestAnimationFrame` 간격이다. 실제 기기의 60 fps와는 다른 값이다.
