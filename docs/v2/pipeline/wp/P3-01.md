# P3-01 서버: PDF 업로드

> 등급: `basic` · 게이트: `full` · 의존: `P3-C` · 소유: `apps/server/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

`LECTERN_PDF=1`이면 업로드 API가 PDF를 엄격하게 받는다: 50 MiB 상한, MIME `application/pdf`, 완성된 파일의 첫 5바이트가 `%PDF-`. 완료되면 `asset.kind = "pdf"` 행이 생기고, `getAssetContent`는 PDF를 `nosniff`·`Content-Disposition: inline`으로 준다. `LECTERN_PDF=0`이면 지금 동작이 한 글자도 바뀌지 않는다.

## 5. 단계

1. `uploads.ts` 상단에 상수를 더한다.
```ts
export const MAX_PDF_BYTES = 50 * 1024 * 1024;
export const PDF_MAGIC = "%PDF-";
```
   `import { config } from "@lectern/config";`를 더한다(이미 있으면 재사용).
2. `createUpload`: `for (const file of body.files)` 검사 루프 안에서, `config().pdf`가 참이고 `file.kind === "pdf"`일 때만 추가 검사한다. 순서는 이 순서다.
   - `file.mime`(`;` 앞, 소문자)이 `application/pdf`가 아니면 `apiError(req.c, 415, "unsupported_media_type", "PDF 파일(application/pdf)만 올릴 수 있습니다.")`.
   - `file.bytes > MAX_PDF_BYTES`이면 `apiError(req.c, 413, "payload_too_large", "PDF는 50MB까지 올릴 수 있습니다.")`.
   - 플래그가 꺼져 있으면 이 블록을 건너뛴다(기존 `storedExtension`·4GB 검사만 탄다).
   - "새 녹음에는 오디오 파일이 하나 있어야 합니다"(400) 검사는 이미 있다. 건드리지 않는다.
3. `completeUpload`: `assemble` 직후, `stored.push(...)` 다음 줄에서 `config().pdf && file.kind === "pdf"`이면 방금 만든 `path`의 앞 5바이트를 읽는다.
```ts
const head = new TextDecoder().decode(new Uint8Array(await Bun.file(path).slice(0, 5).arrayBuffer()));
if (head !== PDF_MAGIC) {
  for (const s of stored) rmSync(s.path, { force: true });
  return apiError(req.c, 400, "bad_request", `${file.filename}은(는) PDF 파일이 아닙니다.`, { file_index: file.index });
}
```
   기존 SHA-256 불일치 처리와 같은 모양으로 쓴다(저장 파일 전부 삭제 후 400). 세션은 `open`으로 남겨 다시 올릴 수 있게 둔다.
4. `insertDocumentAssets`는 고치지 않는다. 이미 `kind = "pdf"`, `mime = "application/pdf"`, `page_count = NULL`로 넣는다. (쪽 수는 P3-03이 채운다. 10절 참고.)
5. `assets.ts`의 `getAssetContent`: `asset.kind === "pdf"`이면 `serveFileWithRange(..., mime, { "Cache-Control": "private, no-store", "X-Content-Type-Options": "nosniff", "Content-Disposition": "inline" })`로 부른다. 다른 종류는 지금 호출 그대로. 플래그와 상관없이 적용한다(헤더만 더하는 변경이다).
6. 테스트를 쓴다(6절). PDF 바이트는 테스트 안에서 `"%PDF-1.4\n" + "x".repeat(n)` 같은 문자열로 만든다(진짜 PDF일 필요 없음). 실제 PDF가 필요한 다른 WP와 달리 이 WP는 `pdf-lib`를 쓰지 않는다.

## 6. 테스트

파일: `apps/server/test/pdf-upload.test.ts` (첫 줄 `import "./preload.ts";`). 헬퍼는 `api-v2-data.test.ts`의 `api()`를 본떠 복사한다. 각 테스트 앞뒤로 `process.env.LECTERN_PDF`를 정하고 `resetConfigForTests()`, `afterAll`에서 `delete` 후 reset.

| 테스트 이름 | 준비 | 기대 |
|---|---|---|
| audio plus pdf in one recording | 플래그 `1`. 파일 2개(오디오 1000바이트 `.m4a`, PDF `%PDF-1.4\n`+100바이트)로 세션 생성 → 파트 업로드 → complete | 200, `GET /recordings/{id}`의 `assets`에 `kind:"pdf"` 1개(`mime:"application/pdf"`, `bytes` 일치) |
| pdf only without recording is 400 | 플래그 `1`. `files:[pdf]`만, `recording_id` 없음 | 생성 요청이 400(`bad_request`) |
| pdf attached to an existing recording | 플래그 `1`. 위 녹음의 `recording_id`로 PDF 1개만 업로드 | complete 200, 같은 녹음의 pdf asset이 2개 |
| oversize pdf is 413 | 플래그 `1`. PDF `bytes: 50*1024*1024 + 1`로 세션 생성(본문은 올리지 않음) | 413 `payload_too_large` |
| exactly 50 MiB is accepted at create | 플래그 `1`. `bytes: 50*1024*1024` | 201 |
| wrong mime is 415 | 플래그 `1`. `kind:"pdf"`, `mime:"text/plain"`, `filename:"a.pdf"` | 415 `unsupported_media_type` |
| bad magic bytes is 400 | 플래그 `1`. 내용이 `"HELLO"...`인 PDF를 complete | 400, `DATA_DIR/uploads`에 방금 만든 파일이 남지 않음, 세션 상태 `open` |
| flag off keeps today's behaviour | 플래그 `0`. mime `text/plain`·내용 `HELLO`인 `.pdf` 파일을 오디오와 함께 complete | 200(지금처럼 받는다), 413·415·400 검사가 걸리지 않음 |
| pdf content headers | 플래그 `1`. 업로드한 pdf asset의 `GET /assets/{id}/content` | 200, `content-type: application/pdf`, `x-content-type-options: nosniff`, `content-disposition: inline` |
| audio content unchanged | 오디오 asset `GET .../content` | `content-disposition`에 `inline` 없음(기존 값 그대로) |
| pdf of another user is 404 | 다른 사용자 토큰으로 pdf asset 요청 | 404 |

## 10. 명세 작성자 메모

- **충돌**: CATALOG는 "플래그 끔에서는 지금의 거절 그대로"라 쓰지만 실제 코드(`storedExtension`, `insertDocumentAssets`)는 이미 PDF를 오디오와 함께 **받는다**(웹 업로드 화면도 보낸다). D-0-3(꺼짐 = 기존 동작)에 따라 꺼짐에서는 현재 동작을 그대로 두고, 새 검사는 켬에서만 건다.
- **해석**: "PDF만 있는 업로드는 400"은 `recording_id` 없는 새 녹음에만 적용했다. 기존 녹음에 PDF만 붙이는 것은 domain `CreateUploadRequest`가 허용하고 쓸모가 있어 허용으로 뒀다.
- **조정**: CATALOG의 "`page_count`" 기록은 쪽 수를 세는 코드(`packages/pdf`)가 P3-02라 P3-01 시점에 없다. `page_count` 채우기는 P3-03으로 넘겼다.
- 500쪽 상한은 업로드 시점에 확인할 수 없어 P3-02가 거절한다.
