# P3-06 PDF 쪽 색인, 쪽 인용, 하이브리드 /search

> 등급: `careful` · 게이트: `full` · 의존: `P3-03` · 소유: `packages/ask/`, `apps/server/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

PDF 쪽이 검색 색인의 조각(`search_chunk.kind = 'pdf_page'`)이 되고, 물어보기가 PDF에만 있는 내용을 쪽 인용(`AskPdfPageCitation`)으로 답한다. `GET /search`는 부분 문자열 검색을 버리고 `packages/ask`의 하이브리드 색인(BM25 + 벡터)을 쓰며, 결과에 전사·문서·PDF 쪽 종류가 있다. `LECTERN_ASK=0`이면 지금의 부분 문자열 검색으로 돌아간다. 범위 밖(다른 사람의 비공개 녹음, 다른 워크스페이스) PDF는 절대 나오지 않는다.

## 5. 단계

1. **색인 입력(서버).** `ask/pdf-sources.ts`:
```ts
export function pdfSourcesOf(recordingId: string): NonNullable<RecordingSources["pdfs"]>;
```
   `SELECT a.id AS asset_id, p.page_no, p.text FROM pdf_page p JOIN asset a ON a.id = p.asset_id WHERE p.recording_id = ? AND a.kind = 'pdf' ORDER BY a.part_index, a.created_at, p.page_no`를 asset별로 묶어 `[{ assetId, pages: [{ page: page_no, text }] }]`. 글자가 빈 쪽은 `chunkPdf`가 건너뛴다(그대로 둔다).
2. `index-job.ts`: 색인 입력을 만드는 곳(`lectureSources(lecture)`를 부르는 자리 — P1이 바꿨다면 그 함수)을 찾아 `config().pdf`가 참일 때만 `pdfs: pdfSourcesOf(lectureRecordingId(lecture.id))`를 입력에 더한다. **`reconcileAskIndex`의 `expected`(`chunkRecording(...)`)도 같은 입력을 쓰게 한다.** 안 그러면 PDF 조각이 "낡음"으로 판정돼 작업이 계속 다시 들어간다. `config().pdf` 거짓이면 `pdfs` 키를 넣지 않는다(= 기존 PDF 조각을 건드리지 않는다).
3. **검색 모듈(ask).** `search.ts`:
```ts
export interface SearchChunkHit { chunk: ChunkRow; snippet: Array<{ text: string; highlight: boolean }>; rrf: number }
export function makeSnippet(text: string, terms: readonly QueryTerm[], radius?: number): Array<{ text: string; highlight: boolean }>;
export async function searchIndex(deps: RetrievalDeps, access: AccessScope, query: string,
  opts?: { kinds?: ChunkKind[]; limit?: number }): Promise<{ hits: SearchChunkHit[]; embeddingTokens: number }>;
```
   - `makeSnippet`: `text.toLowerCase()`에서 각 `term.text`의 첫 등장 위치를 찾고(없으면 앞 `radius*2`자), 가장 이른 위치 앞뒤 `radius`(기본 80)자를 자른다. 그 안의 모든 `term.text` 등장을 `highlight: true` 조각으로 나눈다. 잘린 앞뒤에는 `…`를 붙인다. 이어 붙이면 잘린 원문과 같아야 한다(`…` 제외). 빈 `text`는 `[]`.
   - `searchIndex`: `retrieve(deps, access, query, { limit: opts.limit ?? 50, perRecordingCap: 5 })`. `kinds`가 있으면 `limit: 100`으로 가져온 뒤 걸러 `limit`개만 남긴다. 각 조각은 `hasEvidence`와 같은 기준으로 거른다: `coverage >= Math.min(RETRIEVAL.minTermCoverage, 2 / Math.max(1, terms.length))` 또는 `cosine >= RETRIEVAL.minCosine`.
4. **라우트(서버).** `search.ts`: 기존 `searchRouter`를 `export function createSearchRouter(getService: () => AskService | null)`로 바꾼다(`markdownParagraphs` 내보내기는 유지). `index.ts`: `RESOURCE_ROUTERS`에서 `searchRouter`를 빼고 `v2.route("/", createSearchRouter(options.askService ?? askService))`를 `createAskRouter` 옆에 더한다.
   - `service = getService()`가 `null`이면 **기존 구현 코드를 그대로** 실행한다(함수 `substringSearch(req)`로 옮기기만 한다. 본문 불변).
   - 아니면: `requireWorkspace(req, workspace_id)`; 범위 = `q.recording_id`가 있으면 `{ kind: "recording", recording_id }`, 없으면 `{ kind: "workspace" }`; `resolveAccessScope({ workspaceId, caller: { userId, role: roleIn(...) }, scope, recordings: recordingRows(workspaceId), folders: folderRows(workspaceId), roles: ["owner","admin","member","viewer"] })`. `isScopeError`이면 `not_found`는 404, `forbidden`은 403으로 `apiError`.
   - `q.kind`가 `recording`뿐이면 색인을 부르지 않는다. 그 밖에는 `searchIndex({ db, embedder: service.deps.embedder, vectorIndex: service.deps.vectorIndex, queryCache: service.deps.queryCache }, access, q.q, { kinds })`(`kind` 필터 `transcript`/`document`/`pdf_page`는 그대로 `kinds`). 임베딩 토큰이 0보다 크면 `service.deps.onModelCall`에 `ask_embed` 기록(`runner.ts`의 `recordEmbedding`과 같은 필드, 단가는 `service.deps.price`, 없으면 비용 0).
   - 제목 검색: `kind`가 없거나 `recording`이면 접근 가능한 녹음 제목의 부분 문자열(소문자) 일치를 `RecordingSearchHit`로 맨 앞에 둔다(제목은 색인에 없다).
   - 조각 → 적중 매핑(응답은 `okPage`가 스키마로 검증한다): `transcript` → `{ kind, recording_id, recording_title, snippet, segment_idx: chunk.startIdx, start_ms: chunk.startMs }`; `pdf_page` → `{ …, asset_id: chunk.assetId, page: chunk.page }`; `document` → `{ …, document_id: chunk.documentId, block_id: chunk.blockId ?? "md-" + n }`. 구조화 문서가 아닌 조각(`blockId` null)의 `n`은 그 문서 현재 버전 `rendered_md`를 `markdownParagraphs`로 나눠 조각 `text`의 첫 줄(비어 있지 않은 첫 줄)을 포함하는 첫 문단의 번호이고, 못 찾으면 0이다.
   - 같은 `(recording_id, kind, 위치)` 중복은 한 번만. 최대 50개를 `okPage`에 넘긴다.
5. **인용 확인(코드 변경 없음이 기본).** `toCitation`·`verifyAnswer`는 이미 `pdf_page`를 안다. 6절 테스트가 통과하는데 코드가 부족하면 그때만 `packages/ask/src/citations.ts`를 고친다.
6. README의 검색 줄을 "색인이 있으면 하이브리드, `LECTERN_ASK=0`이면 부분 문자열"로 고친다.

## 10. 명세 작성자 메모

- PDF 조각화(`chunkPdf`), `indexedKinds`의 `pdf_page`, `toCitation`의 `pdf_page`는 `packages/ask`에 **이미 있다.** 이 WP의 실제 일은 서버가 색인 입력에 PDF를 넣는 것, 검색 모듈·라우트, 테스트다.
- `P1`이 색인 입력을 만드는 코드를 바꿨을 수 있다(전사·문서 조각). 3절 `git grep`으로 찾고 계약과 어긋나면 `BLOCKED`.
- **빈틈(다른 WP)**: 이미 있는 녹음에 PDF만 나중에 붙이면(`recording_id` 업로드) `process` 작업이 돌지 않아 PDF가 읽히지도 색인되지도 않는다. P3-01/P3-03 범위에 없다. 조정자가 결정할 것.
- 검색은 입력마다 질의 임베딩 비용이 든다(`QueryEmbeddingCache`가 같은 질의만 막는다). 요청 속도 제한은 이 명세에 넣지 않았다. P3-09의 디바운스에 기댄다.
- 검색 범위가 `ready`·`partial` 녹음으로 좁아진다(`canReadRecording`). 지금의 부분 문자열 검색은 처리 중인 녹음도 훑는다.
- `LECTERN_PDF=0`으로 내려도 이미 색인된 PDF 조각은 남는다(검색에 계속 나온다). 지우는 일은 하지 않는다.
- 도메인에 `rate_limited` 오류 코드는 있으나 이 WP는 쓰지 않는다.
