# P7-05 인계 문서 맞추기

> 등급: `basic` · 게이트: `quick` · 의존: `P7-01`, `P7-02` · 소유: `AGENTS.md`, `docs/`, `README.md`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

처음 온 사람이 `AGENTS.md`와 런북만 읽고 로컬 실행, 테스트, 배포, 롤백을 할 수 있게 문서를 **지금의 코드에 맞춘다.** 파이프라인이 끝난 시점의 저장소 지도, 설계 문서 목차, 로드맵의 단계 상태, 인계 점검표, 상태표 최종본을 쓴다. 문서에 적는 명령은 전부 실제로 실행해 확인하고(실행할 수 없는 것은 그렇다고 적는다), 깨진 링크는 0개여야 한다.

이 작업은 **문서만** 고친다.

## 5. 단계

1. **사실 모으기**(쓰기 전에). 아래 명령의 출력을 스크래치 파일에 모아 둔다.
   ```bash
   git ls-files | awk -F/ 'NF>2 {print $1"/"$2"/"$3} NF<=2 {print $0}' | sort -u | head -200
   ```
   ```bash
   bun -e 'const p = JSON.parse(await Bun.file("package.json").text()); for (const [k, v] of Object.entries(p.scripts)) console.log(k, "=>", v)'
   ```
   ```bash
   git grep -n "^  [a-z-]*:$" -- .github/workflows/ci-cd.yml
   ```
   ```bash
   bun run pipeline status
   ```
2. `AGENTS.md`의 **저장소 지도**를 실제 디렉터리에 맞춘다.
   - 지금 지도에 없는 것을 더한다(있는 것만): `apps/web/`, `apps/apple/`, `packages/domain/`, `packages/harness/`, `packages/media/`, `packages/design-tokens/`, `scripts/pipeline/`, `scripts/load/`, `scripts/rehearse/`, `scripts/bench/`, `docs/v2/pipeline/`, 그리고 `apps/server/src/`에서 새로 생긴 큰 모듈(예: `process-job.ts`, `calendar/`, `google/`, `apple/`, `apns/`, `export/`, `oauth/`). 한 줄에 "무엇이고 언제 고치는가".
   - 사라진 것을 뺀다(`ui.ts`가 줄었거나 없어졌으면 그 설명, "(… 는 v2에서 추가된다)" 줄).
   - **없는 경로를 적지 않는다.** 줄마다 `ls <경로>`로 확인한다.
   - "가장 중요한 규칙", "코딩 규칙", "운영 데이터와 개인정보" 절의 **규칙 문장은 바꾸지 않는다.** 경로·명령이 틀렸을 때만 그 부분을 고친다.
3. `AGENTS.md`의 **개발과 테스트**: 명령을 하나씩 실행해 확인하고 맞춘다 — `bun install`, `bun run typecheck`, `bun test`, 파일 하나 테스트, 웹(`bun run web:build`, `bun run web:e2e`), 게이트(`bash scripts/pipeline/gate.sh quick|unit|full`), 로컬 서버(샌드박스 환경 변수를 준 형태로 적는다. 기본 데이터 디렉터리가 `<repo>/data`라는 경고는 남긴다), Apple(`bash apps/apple/scripts/gate.sh` — Xcode가 있어야 한다는 조건과 함께), Android(`cd apps/android && ./gradlew testDebugUnitTest assembleDebug`), 부하·리허설·벤치 스크립트의 위치(명령은 각 README로 링크).
4. `AGENTS.md`의 **문서** 절: 파이프라인 문서(`docs/v2/pipeline/README.md`), 상태표, 인계 점검표 링크를 더한다.
5. `README.md`(루트): 60줄 이내로 다시 쓴다 — 한 문단 소개(음성 녹음과 참고 PDF로 구조화 노트를 만드는 서비스), 구성(서버·워커·웹·네이티브), 빠른 시작(`AGENTS.md`의 "개발과 테스트"로 링크. 명령을 두 군데에 복사하지 않는다), 문서 지도(AGENTS → docs/v2/README → 런북 → 파이프라인), 라이선스. 개인 값(이메일, 실제 이름, 호스트 이름)을 넣지 않는다. 운영 주소를 이미 적고 있었다면 그대로 둔다(새로 더하지 않는다).
6. `docs/v2/README.md`: 목차를 실제 파일에 맞춘다(설계 문서, ADR 표 — `docs/adr/`의 모든 파일이 표에 있어야 한다, 런북, 파이프라인 문서, `PARITY.md`·`PARITY-ADMIN.md`·`SECURITY-REVIEW.md`·`A11Y-AUDIT.md`가 있으면 그것도).
7. `docs/v2/ROADMAP.md`: `### P0`…`### P7` 제목 바로 아래에 상태 줄을 한 줄씩 넣는다(이미 있으면 고친다).
   ```
   > 상태(YYYY-MM-DD): 구현됨 · 가짜로 테스트함 · 실측 필요: <한 줄> · 사용자 필요: <한 줄>. 자세한 것은 [STATUS](pipeline/STATUS.md).
   ```
   - 단계의 모든 작업이 `merged`면 `구현됨`, 아니면 `부분 구현(<남은 작업 id>)`.
   - 로드맵의 계획 문장(무엇을 할지)은 고치지 않는다. "했다"로 바꿔 쓰지 않는다.
   - "운영 전환 계획"에 한 줄: 통합 브랜치의 내용은 `main`에 합쳐지고 운영 호스트가 살아 있어야 배포된다는 것과, 그 전에 해야 할 일은 인계 점검표 §4에 있다는 것.
8. `docs/v2/pipeline/STATUS.md` 최종본. 구조(네 칸: 만듦 / 가짜로 테스트함 / 실측 필요 / 사용자 필요)는 그대로 둔다.
   - "기준" 줄을 오늘 날짜, 통합 브랜치의 커밋(`git rev-parse --short HEAD`), `pipeline status`의 요약(merged N / blocked N / todo N)으로 바꾼다.
   - 단계별 행을 지금 사실로 다시 쓴다. **"만듦"에는 `merged`인 작업의 결과만 적는다.** `blocked`·`todo`는 행에 id와 이유를 적는다.
   - "가짜로 테스트함"에는 실제 테스트 수를 적는다(`bun test`의 마지막 줄, `bun run web:e2e`의 요약 줄을 실행해 읽는다).
   - "실측 필요"와 "사용자 필요"는 **줄이지 않는다.** 누군가 실제로 확인했다는 기록(날짜, 누가)이 "넘겨받은 요청"이나 런북 기록에 있을 때만 옮긴다.
   - "알려진 결함"·"넘겨받은 요청" 표를 정리한다: 처리된 것은 `처리` 칸에 커밋·작업 id, 안 된 것은 그대로 남긴다. 지우지 않는다.
9. `docs/runbooks/handover-checklist.md`를 쓴다. 다른 런북과 같은 문체. 구조:
   - `## 1. 이 문서의 쓰임` — 새로 온 사람이 위에서 아래로 따라 하며 확인 칸을 채운다. 막히면 그 줄에 무엇이 부족했는지 적는다(그것이 문서 결함이다).
   - `## 2. 읽는 순서` — `AGENTS.md` → `docs/v2/README.md` → `ARCHITECTURE.md` → 런북 목록 → `STATUS.md`. 각 30분 안쪽이라는 기대 시간.
   - `## 3. 로컬에서 해 보기` — 표: 번호 / 할 일 / 명령 / 기대 결과 / 근거 문서 / 확인(날짜·누가·결과). 행:
     1. 의존성 설치(`bun install`)
     2. 타입 검사, 단위 테스트
     3. 웹 빌드와 e2e
     4. 샌드박스로 로컬 서버 띄우고 로그인(임시 디렉터리, 테스트용 오너 환경 변수. 값은 `<임의 값>`으로 적는다)
     5. 짧은 녹음 업로드(가짜 AI로 — e2e 서버나 부하 스크립트의 방법을 가리킨다. 실제 Gemini 호출은 비용이 든다는 경고)
     6. 게이트 `quick`·`unit`·`full`
     7. 환경 변수 하나 추가해 보기(세 곳을 고치는 규칙) — 읽기만
     8. 마이그레이션 만드는 법 — 읽기만
     9. 부하 스크립트 소규모 실행, 복원 리허설을 샌드박스 백업으로 실행
     10. Apple·Android 게이트(도구가 있을 때)
   - `## 4. 운영에서 해 보기 (운영 호스트가 있어야 한다)` — 표 같은 형식. 행: 상태 확인(`/api/health`), 로그 보기, 수동 백업, 복원 리허설(사본), 배포(통합 브랜치 → `main` PR → CD), 롤백, 시크릿 교체 한 가지, 워커 유닛 확인, 기능 플래그 켜고 끄기(`LECTERN_PIPELINE`, `LECTERN_WEB_SHELL` 등 — 켜는 순서와 되돌리는 법), 부하 시험. 각 행은 해당 런북의 절로 링크한다. **이 절의 확인 칸은 비워 둔다**(이 작업을 하는 워커는 운영 호스트에 접근하지 않는다).
   - `## 5. 계정과 외부 서비스` — 무엇이 필요한지와 어디에 절차가 있는지만(값은 적지 않는다): Gemini API 키, Resend, Cloudflare/도메인, Google OAuth 클라이언트와 검증, Apple Developer(Sign in with Apple, APNs 키, Developer ID), GitHub 저장소 시크릿. 각 항목: 무엇에 쓰나 / 어디에 넣나(환경 변수 이름) / 교체 절차 링크 / 없으면 어떤 기능이 꺼지나.
   - `## 6. 확인 기록` — 이 작업에서 워커가 §3을 실제로 해 본 기록. 표: 번호 / 실행한 명령 / 결과(성공·실패·실행 불가와 이유) / 날짜. **실행하지 않은 것을 성공으로 적지 않는다.**
   - `## 7. 알려진 빈 곳` — 문서만으로 안 되는 것(STATUS의 "사용자 필요"에서 가져온다).
10. **명령 확인.** 아래 문서에 나오는 `bash` 코드 블록을 전부 훑어 세 부류로 나눈다.
    - **로컬에서 실행할 수 있는 것**(`bun …`, `git …`, `bash scripts/…`, `./gradlew …`): 실제로 실행한다. 안 되면 문서를 고친다.
    - **운영 호스트에서만 되는 것**(`sudo systemctl …`, `journalctl …`, 운영 경로를 쓰는 것, `ssh`): 실행하지 않는다. 대신 명령이 가리키는 유닛 이름·경로·환경 변수 이름이 저장소의 것(`deploy/systemd/*`, `packages/config/src/index.ts`, `docs/env.md`)과 맞는지 `git grep`으로 대조한다.
    - **비용이 들거나 바깥에 영향을 주는 것**(실제 Gemini 호출, 메일 발송, `git push origin main`, 릴리스): 실행하지 않는다.
    대상: `AGENTS.md`, `README.md`, `docs/runbooks/*.md`, `docs/v2/pipeline/README.md`, `apps/web/README.md`, `scripts/*/README.md`. 결과를 `handover-checklist.md` §6에 적는다(문서별로 "실행 N개 성공, 대조 N개, 실행하지 않음 N개").
11. **링크 검사.** Markdown의 상대 링크가 가리키는 파일이 있는지 본다.
    ```bash
    bun -e 'import { existsSync } from "node:fs"; import { dirname, join, normalize } from "node:path"; const files = (await Bun.$`git ls-files "*.md"`.text()).trim().split("\n"); let bad = 0; for (const f of files) { const text = await Bun.file(f).text(); for (const m of text.matchAll(/\]\(([^)\s]+)\)/g)) { const href = m[1]; if (/^(https?:|mailto:|#)/.test(href)) continue; const path = normalize(join(dirname(f), decodeURIComponent(href.split("#")[0]))); if (path && !existsSync(path)) { bad++; console.log(f + ": " + href); } } } console.log("broken links:", bad); process.exit(bad ? 1 : 0);'
    ```
    - `broken links: 0`이 될 때까지 고친다. 이 작업의 소유(`AGENTS.md`, `docs/`, `README.md`) 밖의 파일에 있는 깨진 링크는 고치지 않고 `handover-checklist.md` §7과 결과 보고의 `NEEDS`에 적는다.
    - 같은 문서 안의 `#앵커`가 실제 제목과 맞는지는 `AGENTS.md`, `docs/v2/README.md`, `handover-checklist.md`, `STATUS.md` 네 파일만 눈으로 확인한다.
12. 마지막 확인: `git diff --stat`에 소유 밖 파일이 없다. 문서에 개인 값(이메일, 실제 이름, 토큰, 비밀번호)이 새로 들어가지 않았다.
    ```bash
    git diff | grep -n "^+" | grep -i -E "@[a-z0-9.-]+\.(com|net|kr)|password=|token=|api[_-]?key=" | grep -v "example.com" ; echo "exit=$?"
    ```
    줄이 나오면 하나씩 보고 실제 값이면 지운다(자리 표시와 환경 변수 이름은 괜찮다).

## 8. 하지 않는 것

- 코드, 테스트, 스크립트, CI, 설정 파일 수정. 문서가 코드와 다르면 **문서를 고친다.** 코드가 틀렸다고 판단되면 `NEEDS`에 적는다.
- 운영 호스트 접속, `main`에 push, 배포.
- 규칙의 변경(`AGENTS.md`의 "가장 중요한 규칙"과 코딩 규칙은 사용자의 것이다).
- 로드맵의 계획을 "완료"로 고쳐 쓰는 것, STATUS의 "실측 필요"를 근거 없이 지우는 것.
- 파이프라인 문서(`CONTRACTS.md`, `CATALOG.md`, `wp/*.md`)의 내용 변경. 깨진 링크만 고친다.
- 새 ADR 쓰기.

## 10. 명세 작성자 메모

- "모든 명령을 실제로 실행"은 운영 호스트 명령과 비용이 드는 명령에는 적용할 수 없다. 그래서 세 부류로 나누고 실행하지 못한 것을 세어 적게 했다(CATALOG의 수용 기준을 좁힌 것이다. CONTRACTS 보충 절).
- 기존 런북에는 호스트의 실제 경로가 들어 있다. 이 작업은 그것을 바꾸지 않는다(운영자가 쓰는 값이다). 새로 쓰는 문서에는 넣지 않는다.
- 인계 점검의 마지막 판정("처음 온 사람이 할 수 있었다")은 실제로 처음 온 사람이 해 봐야 한다. 이 작업이 끝나도 그 칸은 비어 있다(STATUS "사용자 필요: 인계 점검을 해 볼 사람").
- 이 작업은 다른 작업이 모두 끝난 뒤에 돌리는 것이 맞다. `pipeline.json`의 의존은 `P7-01`, `P7-02`뿐이므로, 오케스트레이터가 순서를 마지막으로 잡는다(ORCHESTRATOR에 적었다).
