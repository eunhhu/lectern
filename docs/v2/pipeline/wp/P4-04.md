# P4-04 자동 등록과 재처리 멱등성

> 등급: `basic` · 게이트: `full` · 의존: `P4-03`, `P1-12` · 소유: `apps/server/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

워크스페이스 설정 "일정 자동 등록"이 켜져 있으면, 노트가 발행될 때 날짜가 확실한 일정이 자동으로 수락되고 Google 캘린더 동기화가 큐에 들어간다. 꺼져 있으면(기본) 전부 제안으로 남는다. 같은 녹음을 다시 처리해도 Google 일정 수가 늘지 않는다는 것을 테스트로 고정한다(로드맵 P4 종료 기준).

- 레시피: `RECIPES.md` R3, R12
- 코드: `apps/server/src/notes-publish.ts` — `publishNotes` (P1-11이 만든다)

- 표: `event_candidate`(`resolution_json`, `flags_json`, `confidence`, `status`)

## 5. 단계

1. `calendar/auto-accept.ts`
   ```ts
   /** Accepts the events of one recording that qualify for auto-add (D-P4-1). Returns how many it accepted. */
   export function autoAcceptEvents(recordingId: string, workspaceId: string): number
   /** Called right after publishNotes. Never throws: failures are logged and swallowed. */
   export function afterNotesPublished(recordingId: string, workspaceId: string): void
   ```
   - `autoAcceptEvents`: `config().calendar`가 거짓이면 0. 워크스페이스의 `settings_json`을 `WorkspaceSettings.safeParse`로 읽어 `calendar_auto_add?.enabled`가 참이 아니면 0. 참이면 그 녹음의 `event_candidate` 중 다음을 **모두** 만족하는 행을 `status = 'accepted', updated_at = now`로 바꾼다.
     - `status = 'suggested'`
     - `json_extract(resolution_json, '$.method') = 'parser'`
     - `flags_json = '[]'`
     - `confidence >= min_confidence`
     - `start_at >= now` (지난 일정은 자동 등록하지 않는다)
   - `afterNotesPublished`: `autoAcceptEvents`를 부른 뒤, `config().calendar`가 참이면 수락 건수와 상관없이 `enqueueCalendarSyncForWorkspace(workspaceId)`를 부른다(다시 발행으로 사라진 일정을 Google에서 지우기 위해서다). 전체를 `try/catch`로 감싸 `logger.warn`만 남긴다. 발행된 노트를 캘린더 문제로 실패시키지 않는다.
2. `publishNotes`를 부르는 두 곳에서 발행이 성공한 바로 다음 줄에 `afterNotesPublished(recordingId, workspaceId)`를 넣는다. `publishNotes` 자체(트랜잭션 안)는 고치지 않는다.
3. `updateWorkspace`: `body.settings`가 있으면 기존 `settings_json`을 파싱한 객체에 **얕게 합친다**(`{ ...old, ...body.settings }`). 지금은 통째로 덮어써서 `calendar_auto_add`만 보내면 `reminders`가 사라진다. 값이 `null`인 키는 지운다.

## 6. 테스트

`calendar-auto-accept.test.ts` (`LECTERN_CALENDAR=1`, 가짜 Google. 일정 행은 직접 넣는다)

| 테스트 이름 | 준비 | 기대 |
|---|---|---|
| "off by default: everything stays suggested" | 설정 없음, 조건에 맞는 일정 2개 | `autoAcceptEvents` 0, 둘 다 `suggested` |
| "accepts only qualifying events" | `enabled: true, min_confidence: 0.8`. 일정 5개: ① parser·깃발 없음·0.9·미래 ② `method: "model"` ③ 깃발 `["ambiguous_date"]` ④ 신뢰도 0.7 ⑤ 과거 | ①만 `accepted` |
| "flag off" | `LECTERN_CALENDAR=0`, 설정 켬 | 0 |
| "afterNotesPublished enqueues a sync" | 설정 켬, 활성 연동 1개 | `calendar_sync` 작업 1개 |
| "afterNotesPublished never throws" | 워크스페이스 `settings_json`을 `"{"`(깨진 JSON)로 | 던지지 않는다 |
| "reprocess does not add Google events" | 설정 켬. 일정 2개 발행 → `afterNotesPublished` → `runCalendarSync` → 같은 결과로 다시 발행(`publishNotes`를 한 번 더) → `afterNotesPublished` → `runCalendarSync` | 가짜 캘린더의 일정 수가 2 그대로, `insert` 요청 2회 그대로 |
| "an event dropped by a republish is removed" | 위 뒤, 일정 1개만 있는 결과로 다시 발행하되 빠진 일정을 미리 `suggested`로 되돌려 둠 | 동기화 뒤 Google에 1개 |
| "updateWorkspace merges settings" | `reminders`가 있는 워크스페이스에 `{ settings: { calendar_auto_add: {…} } }` | 응답의 `settings`에 둘 다 있다 |
| "updateWorkspace removes a key with null" | `{ settings: { reminders: null } }` | `reminders`가 없다 |

`publishNotes`에 줄 `NotesResult`는 P1-11의 테스트 파일(`apps/server/test/notes-publish.test.ts`)이 쓰는 생성 도우미를 가져다 쓴다.

## 10. 명세 작성자 메모

- `updateWorkspace`가 `WorkspaceSettings`에 없는 키를 거절하는지는 domain 요청 스키마에 달렸다. `null`로 키를 지우는 것이 스키마에서 막히면(`reminders: null`이 무효) 그 테스트를 빼고 `DEVIATIONS`에 적는다.
- "지난 일정은 자동 등록하지 않는다"는 계약에 없는 이 명세의 추가 조건이다.
