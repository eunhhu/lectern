## 5. 단계

1. `mail.ts`
   ```ts
   export function resolveResendApiKey(): string   // moved from index.ts unchanged (same env → credentials-file order)
   export async function sendMail(m: { to: string; subject: string; html: string }): Promise<{ id?: string }>
   ```
   `sendMail`은 지금의 `fetch("https://api.resend.com/emails", …)` 부분 그대로다. 키가 없으면 지금과 같은 문구로 던진다. 실패 문구도 그대로다. `index.ts`의 `sendResendVerificationEmail`은 제목·HTML을 만든 뒤 `sendMail`을 부르고 `{ sent: true, id }`를 돌려준다. **가입·재설정 메일의 제목과 본문은 한 글자도 바꾸지 않는다.**
2. `reminders.ts`
   ```ts
   export const REMINDER_JOB_KIND = "reminder";
   export function reminderSettings(workspaceId: string): { email: boolean; leadMinutes: number[] }  // absent → { email: false, leadMinutes: [] }; email on with no lead → [1440]
   export function syncRemindersForEvent(eventId: string): void
   export function syncRemindersForActionItem(actionItemId: string): void
   export function syncRemindersForWorkspace(workspaceId: string): void       // after the setting changed
   export async function sendDueReminders(now?: number): Promise<{ sent: number; failed: number; skipped: number }>
   export function reminderMail(r: { kind: "event" | "action_item"; title: string; at: number; allDay: boolean; tz: string; recordingId: string; recordingTitle: string }): { subject: string; html: string }
   export function pruneReminders(now?: number): number   // deletes sent/canceled/failed rows older than 90 days
   ```
   행 계산 규칙(`syncRemindersFor…`)
   - 받는 사람은 그 녹음을 만든 사용자(`recording.created_by`)다.
   - 대상이 알림 조건에 맞으면(일정: `status IN ('accepted','synced')` / 할 일: `status = 'open'`이고 `due_at`이 있음) 그리고 설정의 `email`이 참이면, `lead_minutes`마다 `send_at = 기준 시각 - lead × 60000`을 계산한다(기준 시각은 `start_at` 또는 `due_at`). `send_at <= now`인 것은 만들지 않는다. `INSERT … ON CONFLICT DO NOTHING`(유일 제약이 중복을 막는다).
   - 지금 계산한 `send_at` 집합에 없는 그 대상의 `scheduled` 행은 `canceled`로 바꾼다(시각이 바뀌었거나 조건에서 벗어난 경우). `sent` 행은 건드리지 않는다.
   - `syncRemindersForWorkspace`는 그 워크스페이스의 조건에 맞는 일정·할 일 전부와, `scheduled` 행이 있는 대상 전부에 대해 위를 돌린다.
   - `config().calendar`가 거짓이면 세 함수 모두 아무것도 하지 않는다.
   보내기(`sendDueReminders`)
   - `state = 'scheduled' AND send_at <= now`인 행을 `send_at` 순으로 최대 50개 읽는다.
   - 행마다 대상을 다시 읽어 조건을 확인한다. 대상이 없거나 조건에서 벗어났거나 기준 시각이 이미 지났으면 `canceled`(`skipped`)로 한다. **지난 일의 알림은 보내지 않는다.**
   - 먼저 `UPDATE reminder SET state = 'sent', sent_at = now WHERE id = ? AND state = 'scheduled'`로 차지하고(바뀐 행이 0이면 건너뜀), 그다음 `sendMail`을 부른다. 실패하면 `state = 'failed'`로 바꾼다(다시 보내지 않는다. 두 번 보내는 것보다 한 번 놓치는 쪽을 택한다).
   - 사용자의 이메일은 `users.email`이다. 로그에는 리마인더 id와 결과만 남긴다(주소·제목 없음).
   메일(`reminderMail`)
   - 제목: 일정 `[Lectern] 일정 알림: <제목>`, 할 일 `[Lectern] 할 일 마감 알림: <내용 앞 60자>`.
   - 본문(HTML, 값은 `escapeHtml`): 제목, 시각(`Intl.DateTimeFormat("ko-KR", { timeZone: tz, dateStyle: "long", timeStyle: "short" })`. 하루 종일이면 날짜만), `출처 녹음: <녹음 제목>` 링크(`${config().baseUrl}/app/recordings/<recordingId>`), 끄는 법 한 줄 `이 알림은 Lectern 설정의 "알림"에서 끌 수 있습니다.`와 링크 `${config().baseUrl}/app/settings#reminders`.
3. 호출 지점
   - `updateCalendarSuggestion`, `batchCalendarSuggestions`: 바꾼 일정마다 `syncRemindersForEvent`.
   - `updateActionItem`: `syncRemindersForActionItem`.
   - `updateWorkspace`: `settings.reminders`가 요청에 있으면 `syncRemindersForWorkspace`.
   - 노트 발행 뒤(일정이 자동 수락되거나 할 일이 새로 생김): `P4-04`의 `afterNotesPublished`가 있으면 그 안에서, 없으면 `publishNotes`를 부르는 곳에서 `syncRemindersForWorkspace(workspaceId)`를 부른다. 그 파일이 아직 없으면(P1-12 미병합) 이 호출은 건너뛰고 `NEEDS`에 적는다.
4. 작업: `registerJobHandler(REMINDER_JOB_KIND, …)`가 `sendDueReminders()`와 `pruneReminders()`를 부른다. 서버 시작 때 `startMaintenanceSchedule` 옆에서 5분마다 `enqueueJob`으로 `reminder` 작업(subject `"due"`)을 넣는다. 같은 작업이 대기·실행 중이면 넣지 않는다. `config().calendar`가 거짓이면 주기를 시작하지 않는다. 타이머는 `unref()`한다.
