# P6-A3 LecternKit: 재개 가능한 업로드 큐

> 등급: `careful` · 게이트: `apple` · 의존: `P6-A2` · 소유: `apps/apple/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

녹음 파일을 서버에 올리는 대기열을 만든다. 앱이 꺼지거나 네트워크가 끊겨도 이어서 올리고, 이미 올라간 파트는 다시 보내지 않는다. 대기열은 App Group 폴더의 파일이라 공유 확장과 위젯도 같이 읽는다. 업로드는 서버의 v2 파트 방식(만들기 → 파트 PUT → 완료)을 그대로 쓴다.

## 2. 먼저 읽을 것

- 계약: `CONTRACTS.md` D-P6-6(IETF 재개 업로드는 하지 않는다. 파트 단위로 재개한다), D-P6-8(App Group)
- 코드(서버, 읽기만): `apps/server/src/api/v2/uploads.ts` — `createUpload`, `getUpload`, `putUploadPart`, `completeUpload`, `abortUpload`의 요청·응답과 `Idempotency-Key` 처리
- domain: `CreateUploadRequest`, `UploadSession`(파트 크기, 파트 수, 받은 파트 목록), `UploadPartReceipt`, `CompleteUploadResponse`
- 본보기: `apps/web/src/app/upload/upload.ts`(웹이 같은 API를 쓰는 순서와 재개 방법)
- 코드: `Packages/LecternKit`의 `LecternAPI`, `AuthProvider`(P6-A2)

## 5. 단계

1. `UploadJob`
   ```swift
   public struct UploadJob: Codable, Identifiable, Equatable, Sendable {
       public var id: String                 // also the Idempotency-Key (UUID, made once, never changes)
       public var fileRelativePath: String   // relative to the App Group container
       public var fileName: String
       public var mimeType: String
       public var byteCount: Int64
       public var workspaceID: String
       public var folderID: String?
       public var title: String?
       public var recordedAt: Date?          // sent as recorded_at
       public var pdfRelativePaths: [String] // paired PDFs (share extension)
       public var markers: [Marker]          // sent after completion (when the server has the route)
       public var uploadID: String?          // server upload session
       public var partSize: Int?
       public var partsDone: [Int]
       public var state: State               // queued, uploading, completing, done(recordingID), failed(message), waitingForNetwork
       public var attempts: Int
       public var createdAt: Date
       public var updatedAt: Date
   }
   ```
2. `UploadQueueStore`: 대기열은 폴더 `<컨테이너>/UploadQueue/` 아래 항목마다 파일 하나(`<id>.json`)다. 쓰기는 임시 파일에 쓰고 `replaceItemAt`으로 바꾼다(원자적). 읽기는 폴더의 모든 `.json`을 읽고, 깨진 파일은 `<id>.json.corrupt`로 옮긴 뒤 건너뛴다. `init(directory: URL)`로 폴더를 받는다(앱은 App Group 컨테이너, 테스트는 임시 폴더).
3. `UploadPlan`(순수 함수)
   ```swift
   public func partRanges(byteCount: Int64, partSize: Int) -> [Range<Int64>]      // last part may be shorter; empty file → []
   public func remainingParts(total: Int, done: [Int]) -> [Int]                    // ascending, 1-based like the server
   ```
   파트 번호가 0부터인지 1부터인지는 서버 코드에서 확인하고 그대로 따른다.
4. `UploadTransport`
   ```swift
   public protocol UploadTransport: Sendable {
       func create(_ job: UploadJob) async throws -> (uploadID: String, partSize: Int, partsDone: [Int])     // Idempotency-Key: job.id
       func status(uploadID: String) async throws -> [Int]                                                  // parts the server already has
       func putPart(uploadID: String, part: Int, fileURL: URL, range: Range<Int64>) async throws
       func complete(uploadID: String, idempotencyKey: String) async throws -> String                        // recording id
   }
   ```
   실제 구현은 P6-A2의 생성 클라이언트를 쓴다. 파트는 파일을 메모리에 올리지 않고 그 구간만 읽어 보낸다(파트 하나를 임시 파일로 잘라 `URLSession.upload(for:fromFile:)`로 보내고, 끝나면 임시 파일을 지운다).
5. `UploadQueue`(actor)
   ```swift
   public actor UploadQueue {
       public init(store: UploadQueueStore, transport: UploadTransport, containerURL: URL, now: @Sendable () -> Date = Date.init)
       public func enqueue(_ job: UploadJob) throws
       public func jobs() -> [UploadJob]
       public func run() async                       // processes every runnable job, one at a time
       public func retry(_ id: String) throws
       public func remove(_ id: String) throws       // also deletes the local file when the job is done
       public nonisolated var updates: AsyncStream<[UploadJob]> { get }
   }
   ```
   한 항목의 순서
   1. `uploadID`가 없으면 `create`. 서버가 준 `uploadID`, `partSize`, 받은 파트를 저장한다.
   2. `uploadID`가 있으면 `status`로 서버가 가진 파트를 받아 `partsDone`을 **서버 기준으로** 맞춘다(로컬 기록보다 서버가 진실이다).
   3. `remainingParts`를 차례로 `putPart`. 파트 하나가 끝날 때마다 저장한다.
   4. 다 올렸으면 `complete`(같은 `Idempotency-Key`) → `done(recordingID)`.
   오류 처리
   - 네트워크 오류(`URLError`의 연결 끊김·시간 초과 등): `waitingForNetwork`. 다음 `run()` 때 2단계부터 다시.
   - 401: `AuthProvider`가 refresh한 뒤 다음 `run()`에서 다시(파트 요청은 자동으로 다시 보내지 않는다. P6-A2).
   - 404(업로드 세션이 서버에서 사라짐): `uploadID`와 `partsDone`을 지우고 1단계부터.
   - 409 `quota_exceeded`, 413, 415: `failed(서버 문구)`. 자동으로 다시 하지 않는다.
   - 5xx·429: `attempts`를 올리고 다음 `run()`에서 다시. `attempts`가 8을 넘으면 `failed("서버에 올리지 못했습니다. 잠시 뒤 다시 시도해 주세요.")`.
   - 로컬 파일이 없음: `failed("녹음 파일을 찾을 수 없습니다.")`.
   - `done` 항목의 로컬 파일은 지우지 않는다(사용자가 `remove`를 부르거나 앱이 정리한다). 실패한 항목의 파일은 절대 지우지 않는다.
6. `BackgroundUploader`(iOS·macOS 공통. 플랫폼 전용 부분은 `#if os(iOS)`)
   - `URLSessionConfiguration.background(withIdentifier: "com.qucord.lectern.upload")`, `sharedContainerIdentifier = "group.com.qucord.lectern"`, `isDiscretionary = false`, `sessionSendsLaunchEvents = true`.
   - 파트 업로드 태스크의 `taskDescription`에 `"<jobID>:<part>"`를 넣는다. 델리게이트의 완료 콜백에서 그 값으로 항목을 찾아 `partsDone`을 갱신하고 다음 파트를 건다.
   - 앱이 다시 실행되면 `getAllTasks`로 진행 중인 태스크를 읽어 대기열과 맞춘다.
   - 이 클래스는 단위 테스트하지 않는다(백그라운드 세션은 테스트 프로세스에서 동작하지 않는다). 로직은 전부 `UploadQueue`에 두고 이 클래스는 연결만 한다. 확인은 `MANUAL_CHECKS.md` 항목이다.
7. `MANUAL_CHECKS.md`에 행을 더한다: "업로드 중 앱을 강제 종료해도 이어서 올라간다", "비행기 모드에서 녹음을 끝내고, 네트워크가 돌아오면 올라간다", "1GB 파일 업로드 중 메모리 사용이 일정하다".

## 10. 명세 작성자 메모

- 백그라운드 `URLSession`의 실제 동작(앱 종료 뒤 이어 올리기)은 게이트로 확인되지 않는다. D-P6-9대로 점검표에 올렸다.
- 마커 전송(`job.markers`)은 서버 라우트(P6-01)가 있어야 한다. 생성 클라이언트에 `createMarker`가 없으면 그 부분은 비워 두고 `NEEDS`에 적는다.
- 파트 번호의 시작(0 또는 1)과 `UploadSession`의 필드 이름은 서버 코드를 읽고 맞춘다.
