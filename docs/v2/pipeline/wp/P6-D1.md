# P6-D1 Android: v2 파트 업로드

> 등급: `careful` · 게이트: `android` · 의존: `P1-12` · 소유: `apps/android/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

Android 앱이 녹음을 v2 업로드 API(`createUpload → putUploadPart → completeUpload`)로 올린다. 파일을 8 MiB 파트로 나눠 보내므로, 3시간짜리 녹음을 올리다 네트워크가 끊겨도 **이미 받은 파트는 다시 보내지 않고** 이어서 올린다. 옛 방식(`/api/ingest/shortcut`)은 설정 스위치 뒤에 남는다. 사용자가 보는 변화: 긴 녹음의 업로드가 끊겨도 처음부터 다시 올라가지 않는다.

## 2. 먼저 읽을 것

- 계약: `CONTRACTS.md` D-P6-6(파트 업로드, IETF 재개 업로드는 하지 않는다), D-P6-5(v1 종료 예고 — `/api/ingest/`가 언젠가 410이 된다)
- domain(읽기만): `packages/domain/src/api/uploads.ts`(`CreateUploadRequest`, `UploadSession`, `UploadPartReceipt`, `CompleteUploadResponse`), `packages/domain/src/api/common.ts`(`ApiError` = `{ "error": { "code", "message" } }`, 헤더 `Idempotency-Key`), `resources.ts`의 `Me`(`personal_workspace_id`), `Folder`, `CreateFolderRequest`
- 서버(읽기만): `apps/server/src/api/v2/uploads.ts` — `createUpload`(같은 `Idempotency-Key`와 같은 본문이면 **기존 세션을 그대로 돌려준다**, 본문이 다르면 409 `idempotency_conflict`), `putUploadPart`(파트 길이가 정확해야 한다. 같은 파트를 다시 보내면 덮어쓴다), `completeUpload`(이미 끝난 세션이면 저장된 결과를 다시 준다. 빠진 파트가 있으면 409 `upload_incomplete`)
- 코드: `apps/android/app/src/main/java/com/qucord/lectern/LecternApi.kt`(`uploadAudio`, `UploadResult`, `isRetryable`, `HttpStatusException`), `UploadWorker.kt`, `PendingUploads.kt`, `LecternSession.kt`, `MainActivity.kt`(로그아웃 줄 근처 — 설정 스위치를 둘 곳)
- 테스트 모델: `apps/android/app/src/test/java/com/qucord/lectern/LecternApiUploadTest.kt`(`ServerSocket`으로 만든 로컬 HTTP 서버)

## 5. 단계

1. `LecternUploadV2.kt` — 모양
   ```kotlin
   data class UploadSessionInfo(
       val id: String,
       val status: String,            // open | completed | aborted | expired
       val partSize: Long,
       val firstPart: Int,            // files[0].first_part
       val partCount: Int,            // files[0].part_count
       val receivedParts: Set<Int>,
       val recordingId: String?
   )

   object LecternUploadV2 {
       const val BASE = "/api/v2"
       fun idempotencyKey(itemId: String, generation: Int): String          // generation 0 -> itemId, else "$itemId-g$generation"
       fun partRange(fileBytes: Long, partSize: Long, firstPart: Int, part: Int): Pair<Long, Long>   // (offset, length)
       fun missingParts(session: UploadSessionInfo): List<Int>              // ascending
       fun createBody(workspaceId: String, filename: String, mime: String, bytes: Long, folderId: String?): String

       fun personalWorkspaceId(serverBase: String, token: String, client: String): String                       // GET  /me
       fun folderIdForCourse(serverBase: String, token: String, client: String, workspaceId: String, course: String): String?
       fun createUpload(serverBase: String, token: String, client: String, key: String, body: String): UploadSessionInfo   // POST /uploads
       fun putPart(serverBase: String, token: String, client: String, uploadId: String, part: Int, file: File, offset: Long, length: Long)
       fun complete(serverBase: String, token: String, client: String, uploadId: String, key: String): String   // POST /uploads/{id}/complete -> recording.id

       fun upload(
           serverBase: String, token: String, file: File, course: String, itemId: String, generation: Int,
           client: String, extension: String, mimeType: String,
           onGeneration: (Int) -> Unit = {},
           onProgress: (uploaded: Int, total: Int) -> Unit = { _, _ -> }
       ): UploadResult
   }
   ```
2. 요청 공통 규칙
   - 모든 요청에 `X-Lectern-Token: <token>`과 `X-Client: <client>`(지금 값 그대로: `android-compose`, `android-qstile`, `android-share`). JSON 요청은 `Content-Type: application/json`.
   - 타임아웃: 연결 20초, 읽기 120초.
   - 2xx가 아니면 `HttpStatusException(code, message)`를 던진다. `message`는 응답 JSON의 `error.message`(v2는 `error`가 객체다. v1의 `errorMessage`를 그대로 쓰면 안 된다). 못 읽으면 `HTTP <code>`. 오류 코드 문자열(`error.code`)도 필요하므로 `HttpStatusException`에 `val apiCode: String? = null`을 더한다(기본값이 있어 기존 호출부는 그대로다).
   - 주소 조각의 인코딩은 `java.net.URLEncoder.encode(value, "UTF-8")`(`android.net.Uri`는 단위 테스트에서 동작하지 않는다).
3. `createBody` — 본문은 **매번 글자 하나까지 같아야 한다**(서버가 같은 키의 본문을 비교한다). `JSONObject`의 키 순서에 기대지 말고 문자열을 직접 이어 만든다(`JSONObject.quote`로 값만 이스케이프).
   ```json
   {"workspace_id":"<ws>","recording":{"folder_id":"<folder>"},"files":[{"kind":"audio","filename":"lectern_<itemId>.<extension>","mime":"<mimeType>","bytes":<bytes>}]}
   ```
   `folderId`가 없으면 `"recording":{…},`를 통째로 뺀다. `recorded_at`과 `sha256`은 보내지 않는다(서버가 미디어 메타데이터에서 시각을 읽는다).
4. `folderIdForCourse` — v1의 `course`는 v2에서 폴더 이름이다.
   - `course`가 비어 있으면 `null`.
   - `GET /folders?workspace_id=<ws>&limit=200`을 `next_cursor`가 `null`일 때까지(최대 5쪽) 읽어, `parent_id`가 `null`이고 이름이 `course`와 같은(앞뒤 공백 제거, 대소문자 무시) 폴더의 `id`.
   - 없으면 `POST /folders` `{"workspace_id":"<ws>","name":"<course>"}` → 201의 `id`. 409면(동시에 만들어졌다) 목록을 한 번 더 읽어 찾는다. 그래도 없으면 `null`.
5. `upload` — 순서
   1. `ws = personalWorkspaceId(…)`, `folder = folderIdForCourse(…)`, `body = createBody(…)`.
   2. `session = createUpload(key = idempotencyKey(itemId, generation), body)`.
      - 409이고 `apiCode == "idempotency_conflict"`(본문이 달라졌다: 그 사이 폴더가 생겼다)이거나, 받은 세션의 `status`가 `expired`·`aborted`면: `generation + 1`로 `onGeneration`을 부르고 새 키로 **한 번만** 다시 만든다. 또 그러면 `UploadResult.Rejected(409, …)`.
   3. `status == "completed"`면 파트를 보내지 않고 바로 6으로 간다(완료 응답을 못 받고 끊겼던 경우다).
   4. `missingParts(session)`의 각 파트를 번호 순서로 보낸다: `partRange`로 (offset, length)를 구하고 `PUT /uploads/<id>/parts/<n>`에 `Content-Type: application/octet-stream`, `setFixedLengthStreamingMode(length)`로 파일의 그 구간만 흘려보낸다(`RandomAccessFile.seek(offset)`, 64 KiB 버퍼. **파일 전체를 메모리에 올리지 않는다**). 한 파트가 끝날 때마다 `onProgress(받은 파트 수, 전체 파트 수)`.
   5. `partRange`: `offset = (part - firstPart) * partSize`, `length = min(partSize, fileBytes - offset)`.
   6. `complete(uploadId, key)` → `recording.id`. 409 `upload_incomplete`면 `GET /uploads/<id>`로 세션을 다시 읽어 빠진 파트를 보내고 **한 번만** 다시 완료한다.
   7. `UploadResult.Success(recordingId)`. 녹음 id는 v1의 강의 id와 같은 값이므로(서버 `lectureRecordingId`) 기존 화면 갱신 코드가 그대로 쓴다.
   - 오류 변환: `HttpStatusException` → `UploadResult.Rejected(code, message)`, `IOException` → `NetworkError(message)`, `JSONException` → `NetworkError("서버 응답을 해석할 수 없습니다.")`. `uploadAudio`와 같은 규칙이다.
   - **재개**: 이 함수는 상태를 기억하지 않는다. 다시 불리면 2단계의 `createUpload`가 같은 키로 기존 세션(받은 파트 목록 포함)을 돌려주므로, 빠진 파트만 보내게 된다.
6. `PendingUploads.kt`: `PendingUpload`에 `val uploadGeneration: Int = 0`, `val uploadedParts: Int = 0`, `val totalParts: Int = 0`. `encode`·`decode`에 세 필드를 더한다(`optInt`, 기본 0 — 옛 항목이 그대로 읽힌다).
7. `LecternSession.kt`: `fun useV2Upload(context: Context): Boolean`(키 `use_v2_upload`, 기본 `true`), `fun setUseV2Upload(context: Context, value: Boolean)`.
8. `UploadWorker.doWork`: `LecternSession.useV2Upload(ctx)`가 참이면 `LecternUploadV2.upload(…)`, 아니면 지금의 `LecternApi.uploadAudio(…)`. v2 호출의 콜백:
   - `onGeneration = { g -> PendingUploads.update(ctx, id) { it.copy(uploadGeneration = g, uploadedParts = 0) } }`
   - `onProgress = { done, total -> PendingUploads.update(ctx, id) { it.copy(uploadedParts = done, totalParts = total) } }`
   - 결과 처리(`Success`·`Rejected`·`NetworkError`)는 지금 코드를 그대로 쓴다. 401이면 토큰을 지우는 것도 같다. `Rejected(404, …)`(서버가 v2 API를 모른다: 옛 서버)는 `업로드 거부 (404): …` 뒤에 ` 설정에서 "새 업로드 방식"을 끄고 다시 시도하세요.`를 붙인다.
9. `MainActivity.kt`
   - 로그아웃 줄 근처에 스위치 한 줄: 라벨 `새 업로드 방식`, 설명 `끊겨도 이어서 올립니다. 문제가 있으면 끄세요.` 값은 `LecternSession.useV2Upload`.
   - 대기 목록에서 상태가 `uploading`이고 `totalParts > 1`이면 `업로드 중 (<uploadedParts>/<totalParts>)`를 보인다. 그 밖에는 지금 문구 그대로.
10. `FakeV2Server.kt`(테스트 전용): `LecternApiUploadTest`의 `ServerSocket` 방식을 따른다. 요청 줄·헤더·본문(`Content-Length`)을 읽고 `Connection: close`로 답한다. 기능:
    - `GET /api/v2/me` → `{"personal_workspace_id":"ws_1", …}`
    - `GET /api/v2/folders` → 가진 폴더 목록, `POST /api/v2/folders` → 폴더 추가(201)
    - `POST /api/v2/uploads` → `Idempotency-Key`별로 세션을 기억한다. 같은 키·같은 본문이면 기존 세션, 본문이 다르면 409 `idempotency_conflict`. 파트 계획은 `partSize`(테스트가 정한다. 예: 1024)로 계산
    - `PUT /api/v2/uploads/<id>/parts/<n>` → 길이가 계획과 다르면 400. 맞으면 바이트를 기억한다
    - `POST /api/v2/uploads/<id>/complete` → 빠진 파트가 있으면 409 `upload_incomplete`, 없으면 `{"recording":{"id":"lec_1"}, …}`
    - 조작: `failPartOnce(n, status)`, `dropConnectionOnPart(n)`(본문을 읽다가 소켓을 닫는다), `expire(uploadId)`, `assembled(uploadId): ByteArray`, `requests: List<Recorded>`(메서드, 경로, 헤더)

## 10. 명세 작성자 메모

- CATALOG는 "MockWebServer 테스트"라고 적었지만 저장소에는 그 의존성이 없고 기존 테스트가 `ServerSocket` 서버를 쓴다. 같은 방식을 따르게 했다(새 의존성을 받지 않아도 된다).
- 세션이 만료·취소된 뒤 같은 `Idempotency-Key`로 `createUpload`를 부르면 서버가 그 죽은 세션을 돌려준다. 그래서 키에 세대 번호를 붙이는 규칙을 넣었다. 서버 쪽을 고치는 편이 낫다고 판단되면 STATUS에 적는다(이 작업의 소유가 아니다).
- 서버의 지금 규칙으로는 개인 워크스페이스에만 올릴 수 있다. 그래서 `personal_workspace_id`를 쓴다.
- `recorded_at`을 보내지 않는다. 공유로 들어온 파일은 만든 시각을 앱이 알지 못하고, 본문이 호출마다 같아야 하기 때문이다.
- 실제 기기에서 3시간 녹음을 올리다 끊는 확인은 사용자 몫이다(STATUS "실측 필요").
- `/api/lectures`(목록)는 P6-03의 차단 대상이다. `LECTERN_V1_BLOCK`을 켜기 전에 Android의 읽기 경로도 v2로 옮겨야 한다. 이 파이프라인에 그 작업은 없다(STATUS에 적었다).
