## 5. 단계

1. `scripted-gemini-fetch.ts`:
```ts
export interface ScriptedGeminiTurn {
  parts: Array<Record<string, unknown>>;                 // text / functionCall parts, thoughtSignature allowed
  usage?: { promptTokenCount: number; candidatesTokenCount: number; cachedContentTokenCount?: number };
  finishReason?: string;                                 // default "STOP"
  responseId?: string;
}
export type ScriptedGeminiStep = ScriptedGeminiTurn | ((body: any, index: number) => ScriptedGeminiTurn | Response);
export interface SeenGeminiRequest { url: string; headers: Record<string, string>; body: any }
export function scriptedGeminiFetch(steps: ScriptedGeminiStep[], seen?: SeenGeminiRequest[]): typeof fetch;
export const textPart = (text: string): Record<string, unknown> => ({ text });
export const functionCallPart = (name: string, args: unknown, opts: { id?: string; thoughtSignature?: string } = {}): Record<string, unknown> =>
  ({ functionCall: { ...(opts.id ? { id: opts.id } : {}), name, args }, ...(opts.thoughtSignature ? { thoughtSignature: opts.thoughtSignature } : {}) });
```
   `scriptedGeminiFetch`: 요청마다 `seen`에 `{url, headers(소문자 키), body(JSON.parse)}`를 쌓는다. URL이 `GEMINI_API_BASE`로 시작하지 않으면 `throw new Error("unexpected outbound request: …")`(실제 네트워크 금지). `index`번째 단계가 없으면 `throw new Error("unexpected extra Gemini request")`. 응답은 `text/event-stream`, 본문은 `data: ${JSON.stringify({ candidates: [{ content: { role: "model", parts }, finishReason }], usageMetadata, responseId })}\r\n\r\n` 하나. `usage` 기본값은 `{ promptTokenCount: 1000, candidatesTokenCount: 50 }`. 단계가 함수면 `(JSON.parse(body), index)`로 부르고 `Response`를 돌려주면 그대로 응답한다.
   `index.ts`에 `export * from "./eval/scripted-gemini-fetch.ts";`.
2. `gemini-ask-tools.test.ts`, `tool-loop.test.ts`, `ask-tools.test.ts`를 6절대로 쓴다. 테스트는 먼저 쓴다(WORKER 3절). 통과하지 않는 테스트가 **코드 결함**을 가리키면 `runner.ts`/`gemini-ask.ts`만 최소로 고친다. 기대값이 틀렸다고 생각되면 테스트를 약하게 만들지 말고 `BLOCKED`.

## 10. 명세 작성자 메모

- CATALOG의 "테스트 공급자"를 `packages/harness/src/eval/`의 재사용 가짜 `fetch`로 해석했다(`eval/scripted.ts` 선례). 모델 객체가 아니라 HTTP 경계의 가짜라서 사고 서명 재전송까지 실제 어댑터 코드로 검증된다.
- "질문 1회 상한 초과 시 `budget_exceeded`"는 기존 테스트(첫 호출 전 초과)에 더해 둘째 라운드에서 초과하는 경우를 `inputTokens: 3_333_000`(999,900 µUSD)로 만든다. 이 숫자는 `gemini-3.5-flash-lite` 입력 단가 0.3과 `CONTEXT_BUDGET.maxOutputTokens`가 100 토큰 이상이라는 가정에 기댄다. 가정이 틀리면 `costOf`로 다시 계산해 값을 맞춘다(기대 동작은 같다).
- "폴더 범위" 시험은 `FOLDERS`의 `fld_school`(하위 폴더 포함)을 쓴다. 라운드 상한과 도구 목록이 `access.scope.kind === "recording"`인지로만 갈리는지는 `runner.ts` 코드로 확인했다.
- `read_more` 시험은 `longSources`의 `라운드 로빈` 문장이 윈도 경계 안에 있고 뒤 윈도가 존재한다는 가정이다(319개 세그먼트). 아니면 `neighborChunk`가 null이라 `"결과 없음"`이 나와 테스트가 실패하니, 그때는 질문 문구를 고른 세그먼트 번호만 바꿔 맞춘다.
