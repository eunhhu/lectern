# P0-01 preflight가 / 리다이렉트를 알게 한다

> 등급: `basic` · 게이트: `full` · 의존: 없음 · 소유: `apps/server/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

`LECTERN_WEB_SHELL=1`이면 `/`가 `/app`으로 302를 보낸다(`apps/server/src/http.ts`의 `createHttpApp`). 그런데 `apps/server/src/preflight.ts`의 점검 표는 `["/", 200]`으로 고정이라, 웹 셸을 켠 호스트에서는 배포 사전 점검이 실패한다. 이 작업이 끝나면 점검 표가 플래그에 따라 `/`의 기대 상태를 200(끔) 또는 302(켬)로 바꾸고, 켬일 때 `Location`과 `/?legacy=1`도 확인한다. 게이트의 "플래그 켬" preflight가 통과한다.

## 2. 먼저 읽을 것

- 계약: `CONTRACTS.md` §0.2(플래그), D-P2-6(`?legacy=1`은 유지).
- 레시피: `RECIPES.md` R11(preflight 항목 추가), R12(서버 테스트), R4(config 읽기: `config()`).
- 코드: `apps/server/src/preflight.ts` — `checks` 표, `failures` 배열.
- 코드: `apps/server/src/http.ts` — `createHttpApp`의 `app.get("/")` (302 + `legacy=1` 분기).
- 코드: `apps/server/src/web-shell.ts` — `WEB_SHELL_DIST_DIR`, `webShellResponse` (dist가 없으면 503).
- 코드: `apps/server/test/web-shell.test.ts` — 기존 `/` 리다이렉트 테스트 모양.
- 코드: `docs/v2/pipeline/flags-on.env` — 이미 `LECTERN_WEB_SHELL=1`이 있다.

## 5. 단계

1. `apps/server/src/preflight-checks.ts`를 만든다. 서버 모듈을 import하지 않는다(순수).
   ```ts
   export type PreflightCheck = [path: string, expectedStatus: number];

   /** The `/` row depends on LECTERN_WEB_SHELL: 302 when the web shell redirects, else 200. */
   export function buildPreflightChecks(webShell: boolean, pageScripts: string[]): PreflightCheck[] {
     return [
       ["/api/health", 200],
       ["/", webShell ? 302 : 200],
       ["/admin", 200],
       ["/s/preflight-missing-token", 404],
       ["/api/lectures", 401],
       ["/api/v2/me", 401],
       ["/api/v2/openapi.json", 200],
       ["/privacy", 200],
       ["/terms", 200],
       ...pageScripts.map((n): PreflightCheck => [`/assets/${n}`, 200]),
     ];
   }

   /** Extra checks when the shell is on. `get` answers a request; returns problem strings. */
   export async function rootRedirectProblems(
     get: (path: string) => Promise<{ status: number; location: string | null }>,
     opts: { distBuilt: boolean }
   ): Promise<string[]>;
   ```
   `rootRedirectProblems` 규칙(순서대로, 문제는 한국어 아닌 영어 문자열로 모은다):
   - `get("/")`의 `location`이 `/app`으로 시작하지 않으면 `"/ redirect Location is <값> (expected /app...)"`.
   - `get("/?legacy=1")`의 `status`가 200이 아니면 `"/?legacy=1 → <status> (expected 200)"`.
   - `opts.distBuilt`가 true일 때만 `get("/app")`의 `status`가 200이 아니면 `"/app → <status> (expected 200)"`.
2. `apps/server/src/preflight.ts`를 고친다.
   - `import { config } from "@lectern/config"`와 `import { existsSync } from "node:fs"`, `import { join } from "node:path"`를 넣는다. (`WEB_SHELL_DIST_DIR`는 `await import("./web-shell.ts")`로 가져온다.)
   - `const checks: Array<...> = [...]` 블록을 `const checks = buildPreflightChecks(config().webShell, [...PAGE_SCRIPTS.keys()]);`로 바꾼다.
   - `for (const [path, expected] of checks)` 루프 뒤, `web build` 블록 앞에 추가한다.
     ```ts
     if (config().webShell) {
       const { WEB_SHELL_DIST_DIR } = await import("./web-shell.ts");
       const get = async (path: string) => {
         const res = await handleRequest(new Request(`http://localhost${path}`));
         return { status: res.status, location: res.headers.get("Location") };
       };
       failures.push(...(await rootRedirectProblems(get, { distBuilt: existsSync(join(WEB_SHELL_DIST_DIR, "index.html")) })));
     }
     ```
   - 마지막 `console.log`의 점검 수(`checks.length`)는 그대로 둔다.
3. `apps/server/test/preflight-checks.test.ts`를 만든다(6절). 첫 줄은 `import "./preload.ts";`.

## 6. 테스트

파일: `apps/server/test/preflight-checks.test.ts`

| 테스트 이름 | 준비 | 기대 |
|---|---|---|
| root row is 200 when the shell is off | `buildPreflightChecks(false, [])` | `["/", 200]`을 포함하고 302 행이 없다 |
| root row is 302 when the shell is on | `buildPreflightChecks(true, [])` | `["/", 302]`을 포함하고 `["/", 200]`이 없다 |
| page scripts are appended | `buildPreflightChecks(false, ["a.js"])` | 마지막 행이 `["/assets/a.js", 200]` |
| redirect to /app passes | 가짜 `get`: `/`→302+`/app`, `/?legacy=1`→200, `/app`→200; `distBuilt:true` | 빈 배열 |
| wrong Location is reported | `/` → 302, `Location: /login` | 문제 1건, `"/app"` 포함 |
| legacy root must be 200 | `/?legacy=1` → 302 | 문제에 `"/?legacy=1 → 302"` 포함 |
| /app is skipped when dist is not built | `/app` → 503, `distBuilt:false` | 빈 배열 |
| /app 503 is reported when dist is built | `/app` → 503, `distBuilt:true` | 문제에 `"/app → 503"` 포함 |
| real app: shell on redirects | `createHttpApp(legacy, { webShellDistDir: tmp })`(web-shell.test.ts와 같은 방식, tmp에 `index.html` 파일 생성) → `/`, `/?legacy=1`, `/app` 호출 | 302+`/app`, legacy 응답, 200 |

## 10. 명세 작성자 메모

- CD의 preflight는 `/app` 점검 뒤에야 `stageWebBuild`로 새 웹 앱을 `dist.next`에 만든다. 새 체크아웃에는 `apps/web/dist`가 없을 수 있어 `/app`이 503이 된다. 그래서 `/app` 200 점검은 `dist/index.html`이 있을 때만 한다(카탈로그 문구 "`/app`이 200인지"를 조건부로 해석). 계약과 다르면 오케스트레이터가 정한다.
