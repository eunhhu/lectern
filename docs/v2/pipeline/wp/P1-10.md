# P1-10 전사 발행 (서버)

> 등급: `careful` · 게이트: `full` · 의존: `P1-C` · 소유: `apps/server/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

하네스가 만든 전사(`Transcript`)를 v2 테이블(`transcript_segment`, `speaker`, `transcript_gap`)에 한 트랜잭션으로 발행하는 함수 `publishTranscript`를 만든다. `LECTERN_TRANSCRIPT_ENGINE=on`이면 `transcribe` 작업이 끝날 때 이 함수를 부르고, 전사 색인 작업을 넣고, `recording.updated` 이벤트를 낸다. `shadow`와 `off`에서는 지금처럼 아무 행도 만들지 않는다. 그러면 `GET /recordings/{id}/transcript`(`getTranscript`)가 세그먼트·화자·gap을 돌려준다.

## 5. 단계

1. `apps/server/src/transcript-publish.ts`를 만든다. `queue.ts`처럼 `index.ts`를 import하지 않는다.
   ```ts
   import type { Transcript } from "@lectern/harness";
   export interface PublishTranscriptInput { recordingId: string; workspaceId: string; transcript: Transcript }
   export interface PublishTranscriptResult { segments: number; speakers: number; gaps: number }
   export function publishTranscript(input: PublishTranscriptInput): PublishTranscriptResult
   ```
2. 본문은 `transact(() => { ... })` 한 번(`api/v2/store.ts`). 안에서 순서대로:
   1. `SELECT id, label, display_name FROM speaker WHERE recording_id = ?`로 기존 화자를 읽어 `label → {id, display_name}` 맵을 만든다.
   2. `transcript.speakers`의 각 `label`마다: 맵에 있으면 그 `id`를 쓰고 `UPDATE speaker SET confidence = ?, updated_at = ? WHERE id = ?`(`display_name`은 건드리지 않는다). 없으면 `INSERT INTO speaker (id, workspace_id, recording_id, label, display_name, confidence, created_at, updated_at) VALUES (uuidv7(), ?, ?, ?, NULL, ?, ?, ?)`.
   3. 이번 전사에 없는 `label`의 기존 화자 행은 `DELETE`한다(세그먼트가 가리키지 않게 된 것).
   4. `DELETE FROM transcript_segment WHERE recording_id = ?`, `DELETE FROM transcript_gap WHERE recording_id = ?`.
   5. 세그먼트마다 `INSERT INTO transcript_segment (workspace_id, recording_id, idx, start_ms, end_ms, speaker_id, text, confidence, source_chunk, lang) VALUES (...)`. `speaker_id`는 `label` 맵에서, `confidence`와 `lang`은 `NULL`, `source_chunk`는 세그먼트 값.
   6. gap마다 `INSERT INTO transcript_gap (workspace_id, recording_id, kind, start_ms, end_ms) VALUES (...)`. `kind`는 `break`·`tail`·`missing_transcript` 그대로(실패한 청크는 하네스가 이미 `missing_transcript` gap으로 넣어 준다).
3. 녹음 행이 없으면(`SELECT 1 FROM recording WHERE id = ?`) `Error("recording not found")`를 던진다(트랜잭션 전에 확인).
4. `apps/server/src/transcript-job.ts`의 `runTranscriptJob`: 파이프라인 성공 뒤, 기존 "삭제됐으면 중단" 검사 다음에 `mode === "on"`이면 아래를 한다. `mode === "shadow"`이면 이 블록을 건너뛴다.
   ```ts
   const recordingId = lectureRecordingId(lectureId);
   const published = publishTranscript({ recordingId, workspaceId, transcript });
   scheduleLectureIndex(lectureId, job.ownerId);
   announceLectures([lectureId]);
   ```
   발행이 던지면 `logger.error("could not publish transcript", { ...fields, err })` 하고 작업은 `{ ok: false, error: "전사를 저장하지 못했습니다." }`로 끝낸다.
5. 같은 파일의 `summary.published`를 `mode === "on"`이면 `true`로 바꾸고, `logger.info("transcript stored (shadow)")` 문구는 모드에 맞게 `"transcript stored"`/`"transcript published"`로 나눈다. 파일 머리 주석과 `mode === "on"` 경고(`logger.warn("...runs as shadow until...")`)를 지운다. 기존 테스트가 `published: false`를 `on`에서 기대하므로 4~5의 결과로 `transcript-job.test.ts`의 해당 줄이 바뀌어야 한다. 이 줄만 `published: true`로 고친다(WORKER 규칙 5의 예외, 10절에 기록).
6. `apps/server/src/ask/legacy.ts`: `lectureSources(lecture)`가 `transcript_segment` 행이 있으면 `transcript: { segments, speakers }`를 함께 돌려준다(`SELECT idx, start_ms, end_ms, speaker_id, text FROM transcript_segment WHERE recording_id = ? ORDER BY idx`, 화자 맵은 `speaker.label`/`display_name`). `isIndexable`은 `(status === "done" && markdown.trim() !== "") || 전사 행이 있음`으로 넓힌다. 전사가 없는 강의의 청크 id는 바뀌지 않아야 한다(기존 ask 테스트 통과).

## 6. 테스트

파일: `apps/server/test/transcript-publish.test.ts` (모델: `transcript-job.test.ts`의 `pendingLecture`, `directJob`, `engine`, `beforeAll`의 임베디드 워커 정지). 전사는 손으로 만든 `Transcript` 객체, 공급자는 `ScriptedTranscriptionProvider`. 실제 호출 없음.

공통 준비: `pendingLecture(...)`로 강의를 만들고 `recordingId = lectureRecordingId(id)`. `T` = 세그먼트 3개(`idx` 0,1,2; 화자 `S1`,`S2`,`S1`), `speakers` 2개, gap 1개(`break`, 50_000~60_000).

| 테스트 이름 | 준비 | 기대 |
|---|---|---|
| publishes segments, speakers and gaps | `publishTranscript({recordingId, workspaceId, transcript: T})` 후 `GET /api/v2/recordings/{id}/transcript` (R12 `api()`) | 세그먼트 3개(idx 0..2, `text` 일치), 화자 2개(`label` S1,S2), gaps 1개 `kind: "break"` |
| publishing twice keeps the same row counts | 두 번 호출 | `transcript_segment` 3, `speaker` 2, `transcript_gap` 1 |
| speaker ids are stable across republish | 두 번 호출, 사이에 S1의 id 기록 | 두 번째 뒤에도 S1의 `id` 같고 세그먼트의 `speaker_id`가 그 id |
| user-given speaker names survive | 첫 발행 뒤 `PATCH`(`updateSpeaker`)로 S1 `display_name = "김교수"`, 재발행 | S1 `display_name === "김교수"` |
| failed chunk shows as missing_transcript gap | `T.gaps`에 `{kind:"missing_transcript", start_ms:10_000, end_ms:20_000}` 추가 | 해당 gap 행 존재 |
| removed speaker is deleted on republish | 첫 발행 S1,S2; 두 번째 `T2`는 S1만 | `speaker` 행 1개 |
| on: job publishes, indexes and announces | `engine("on")`, `directJob` + 가짜 공급자로 `runTranscriptJob` (ffmpeg 없으면 `describe.skipIf`) | `transcript_segment` 행 > 0, `job_event`에 `type='updated'` 새 행, 결과 `published: true` |
| shadow and off publish nothing | `engine("shadow")`로 실행 / `engine("off")` | `transcript_segment` 행 0 |
| missing recording throws | 존재하지 않는 `recordingId` | `expect(() => publishTranscript(...)).toThrow()` |
| transcript-only recording is indexable | 전사만 있는 강의(`status` processing) | `isIndexable(...) === true`, `lectureSources(...).transcript.segments.length === 3` |

## 10. 명세 작성자 메모

- 현재 `transcript-job.test.ts`는 `on`에서도 `published: false`를 기대한다. 5단계에서 그 한 줄을 바꾸게 했다(계약 §1.9가 `on`에서 발행을 요구하므로 불가피). 워커는 이 줄 외의 기대값을 약하게 하지 않는다.
- 계약 §1.9는 "전사 색인 작업"을 말하지만 기존 `index` 작업은 `lectures.markdown`만 색인한다. `ask/legacy.ts`의 `lectureSources`를 넓히는 것으로 해석했다(`apps/server/` 소유 안).
- domain에 `transcript.ready` 이벤트가 있으나 서버 이벤트 번역(`api/v2/events.ts`)은 lecture 이벤트만 다뤄서 이번엔 쓰지 않는다. 카탈로그도 `recording.updated`만 요구한다.
