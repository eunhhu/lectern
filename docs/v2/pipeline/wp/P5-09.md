# P5-09 계정 삭제

> 등급: `careful` · 게이트: `full` · 의존: `P5-08` · 소유: `apps/server/`, `apps/worker/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

사용자가 계정 삭제를 요청하면 7일의 유예 기간이 시작된다. 그동안은 평소처럼 쓸 수 있고 취소할 수 있다. 7일이 지나면 작업이 그 사용자의 녹음·파일·색인·토큰·세션·연동과 사용자 행을 지운다. 지운 뒤 그 사용자의 흔적이 어느 테이블에도 남지 않는다는 것을 테스트로 고정한다.

## 5. 단계

1. `account-deletion.ts`
   ```ts
   export const ACCOUNT_DELETION_JOB_KIND = "account_deletion";
   export const DELETION_GRACE_MS = 7 * 24 * 60 * 60 * 1000;
   export function deletionOf(userId: string): { state: "none" | "scheduled"; requestedAt: number | null; executeAfter: number | null }
   export function soleOwnerTeams(userId: string): { id: string; name: string }[]     // team workspaces where the user is the only owner and other members exist
   export function requestDeletion(userId: string, now?: number): { executeAfter: number }
   export function cancelDeletion(userId: string): boolean
   export function enqueueDueDeletions(now?: number): number
   export async function executeDeletion(userId: string, now?: number): Promise<"done" | "skipped">
   export const USER_TABLES: { table: string; column: string }[]    // every table that holds a user id (see step 3)
   ```
2. `me.ts`
   - `requestAccountDeletion`
     1. 확인: 사용자가 비밀번호 로그인을 쓸 수 있으면(`oauth_identity`가 없거나 본문에 `password`가 왔으면) `verifyPassword`가 맞아야 한다. 틀리면 `403 forbidden`, `비밀번호가 올바르지 않습니다.` OAuth로만 가입한 사용자(identity가 있고 `password`가 없음)는 세션이 만들어진 지 10분 이내여야 한다(방금 다시 로그인했다는 뜻). 아니면 `403`, `보안을 위해 다시 로그인한 뒤 10분 안에 요청해 주세요.`
     2. `soleOwnerTeams`가 비어 있지 않으면 `409 conflict`, `"<이름>" 워크스페이스의 유일한 owner입니다. 다른 멤버를 owner로 지정하거나 워크스페이스를 비운 뒤 다시 시도해 주세요.`(`details.workspaces`에 id 목록).
     3. `requestDeletion` → `{ state: "scheduled", requested_at, execute_after }`. 이미 예약돼 있으면 그 값을 그대로 돌려준다(기한을 늘리지 않는다).
     4. 개인 액세스 토큰과 네이티브 access 토큰으로는 부를 수 없다(쿠키 세션만. `req.pat`이 있거나 `via !== "session"`이면 403).
   - `cancelAccountDeletion`: `state = 'canceled'`로 바꾸고 `{ state: "none", requested_at: null, execute_after: null }`.
   - `getAccountDeletion`: `deletionOf`.
   - 유예 중에도 로그인과 모든 기능은 그대로 된다.
3. `executeDeletion(userId)` — 실행 직전에 다시 확인한다: `account_deletion.state = 'scheduled'`이고 `execute_after <= now`가 아니면 `skipped`. `soleOwnerTeams`가 생겼으면 `skipped`(행은 `scheduled`로 둔다. 다음 날 다시 본다). 그다음 순서대로:
   1. Google 연동: 그 사용자의 `integration` 행마다 토큰 폐기(실패해도 계속) → `calendar_event_link` 행 삭제.
   2. 내보내기 파일: 그 사용자의 `data_export` 행의 파일을 지운다.
   3. `USER_TABLES`의 각 테이블에서 그 사용자의 행을 지운다. 목록(있는 테이블만. `sqlite_master`로 존재를 확인하고 없는 것은 건너뛴다): `oauth_identity(user_id)`, `auth_session_meta(user_id)`, `access_token(user_id)`, `native_session(user_id)`, `workspace_invite(invited_by)`, `workspace_invite(accepted_by)`, `data_export(user_id)`, `calendar_feed(user_id)`, `reminder(user_id)`, `integration(user_id)`, `oauth_state(user_id)`, `push_device(user_id)`, `share_link(created_by)`, `recording_marker(created_by)`.
   4. 팀 워크스페이스에 남긴 것: 그 사용자가 만든 **비공개** 녹음은 지운다(다른 사람이 볼 수 없는 데이터다). **공개(`workspace`) 녹음은 워크스페이스에 남기고** `created_by`를 그 워크스페이스의 owner(가장 먼저 owner가 된 사람)로 바꾼다. 멤버가 그 사용자 하나뿐인 팀 워크스페이스는 통째로 지운다(녹음 → `deleteWorkspaceAskData` → `deleteWorkspaceRows`).
   5. `deleteUserAndData(userId)`(개인 워크스페이스의 강의·파일·아카이브·색인·세션·멤버십·사용자 행).
   6. `account_deletion` 행을 지운다(사용자 id가 남지 않게. `state = 'done'`으로 두지 않는다).
   7. `logger.info`에 사용자 id의 sha256 앞 12자만 남긴다(이메일·이름 없음).
   각 단계는 다시 실행해도 안전해야 한다(중간에 죽으면 작업이 처음부터 다시 돈다).
4. 주기: `maintenance.ts`에 `enqueueDueDeletions()` 단계를 더한다(`state = 'scheduled' AND execute_after <= now`인 사용자마다 `account_deletion` 작업, subject = user id, 중복 없이). `registerJobHandler(ACCOUNT_DELETION_JOB_KIND, …, { concurrency: 1 })`.

## 6. 테스트

`account-deletion.test.ts`

| 테스트 이름 | 준비 | 기대 |
|---|---|---|
| "request needs the password" | 틀린 비밀번호 | 403. 맞으면 200 `state: "scheduled"`, `execute_after - requested_at === 7일` |
| "still usable during the grace period" | 요청 뒤 로그인·목록·업로드 | 모두 평소대로 |
| "cancel" | 요청 → 취소 → `getAccountDeletion` | `state: "none"`. `enqueueDueDeletions`가 기한 뒤에도 0 |
| "requesting twice keeps the date" | 하루 뒤 다시 요청 | `execute_after` 그대로 |
| "not before the date" | 기한 전 `executeDeletion` | `skipped`, 사용자 그대로 |
| "sole owner of a team with members" | 팀의 유일한 owner | 409, 문구에 워크스페이스 이름 |
| "tokens cannot request deletion" | PAT·네이티브 토큰으로 요청 | 403 |
| "no trace is left" | 아래 "전수 검사" | 통과 |
| "files and index are gone" | 실행 뒤 | 오디오·아카이브·내보내기 파일 없음, 물어보기 색인에 그 워크스페이스 조각 없음 |
| "team recordings" | 팀에 공개 녹음 1개, 비공개 1개를 가진 멤버를 삭제 | 공개 녹음은 남고 `created_by`가 owner, 비공개 녹음은 없다 |
| "solo team is removed" | 혼자뿐인 팀 워크스페이스 | 워크스페이스 행 없음 |
| "Google token is revoked" | 연동이 있는 사용자(가짜 Google) | `revoked`에 토큰, `integration` 행 없음 |
| "idempotent" | `executeDeletion` 두 번 | 두 번째 `skipped`, 오류 없음 |
| "login fails afterwards" | 실행 뒤 로그인 | 401 |
| "v1 contract" | 기존 `v1-contract.test.ts` | 통과 |

**전수 검사**("no trace is left"): 모든 기능을 한 번씩 쓴 사용자를 만든다(녹음·문서·전사·일정·할 일·물어보기 대화·공유 링크·PAT·네이티브 세션·identity·세션 메타·ICS feed·리마인더·내보내기·초대 보낸 기록). `executeDeletion` 뒤에 `sqlite_master`에서 모든 테이블을 읽고, 테이블마다 모든 `TEXT` 열에 대해 `SELECT COUNT(*) FROM <t> WHERE <col> = ? OR <col> = ?`(사용자 id, 개인 워크스페이스 id)을 돌린다. 합이 0이어야 한다. 이메일로도 같은 검사를 한다. 허용 목록은 없다(감사 로그에 사용자 id가 남는 구조면 그 행의 id 열을 비우거나 지우는 처리를 3단계에 더한다. 감사 로그 테이블은 v1 소관이므로 행 삭제만 하고 스키마는 바꾸지 않는다).

## 10. 명세 작성자 메모

- 팀 워크스페이스의 공개 녹음을 남기고 소유자를 바꾸는 것은 계약에 없는 이 명세의 결정이다(계약은 "개인 워크스페이스의 녹음…을 지우고"라고만 했다). 방침 문구("계정과 개인 워크스페이스의 녹음·문서·파일을 지웁니다")와 맞는다.
- `USER_TABLES`에는 이 작업보다 뒤에 생기는 테이블(`push_device`, `recording_marker`)도 적었다. 없으면 건너뛴다. P6-01은 로그아웃·계정 삭제 때 푸시 기기를 지워야 하는데, 이 목록에 있으므로 따로 고칠 것이 없다.
- 감사 로그(`recordAuditLog`가 쓰는 테이블)에 사용자 id·이메일이 남는지는 확인하지 않았다. 전수 검사가 잡아낸다.
- OAuth 전용 사용자의 "10분 이내 세션" 규칙은 세션 생성 시각(`sessions.created_at`)으로 본다.
