# P7-01 부하 시험 스크립트

> 등급: `basic` · 게이트: `unit` · 의존: `P1-12`, `P1-16` · 소유: `scripts/load/`, `docs/runbooks/`
> (이 줄은 `pipeline.json`의 값과 같아야 한다.)

## 1. 목표

서버가 실제 부하에서 어떻게 버티는지 재는 스크립트 세 개를 만든다: 동시 업로드 N건(`uploads.ts`), 3시간 길이 녹음 한 건(`long-recording.ts`), 디스크가 거의 찬 상태(`disk-full.ts`). 셋 다 임시 디렉터리의 샌드박스 서버를 띄우고, 합성 오디오를 올리고, JSON 요약(걸린 시간, 실패, 서버 최대 메모리)을 낸다. AI는 가짜이거나 아예 돌지 않는다. 실제 데이터 디렉터리를 쓰려 하면 거절한다. Raspberry Pi에서 돌리는 법은 런북에 적는다(돌리는 것은 사용자다).

- domain(읽기만): `packages/domain/src/api/uploads.ts`

- 런북: `docs/runbooks/incident-response.md` §3.3(디스크 부족), `docs/runbooks/host-setup.md`

둘째 명령에 결과가 없으면 멈춘다(P1-16이 먼저다. 이 작업의 의존이다). 스크립트 자체는 그 경로가 없는 서버를 만나도 죽지 않고 `processing: "unavailable"`로 요약한다(5절. 옛 커밋에서 돌릴 때를 위한 방어다). `ffmpeg`가 없으면 5절의 합성 오디오가 순수 TypeScript WAV로 대체된다.

## 5. 단계

1. `lib/guard.ts`
   ```ts
   /** Throws unless `dir` is safe to use as a throwaway data root. */
   export function assertSandboxDir(dir: string, env: Record<string, string | undefined> = process.env): string   // returns the resolved path
   ```
   거절하는 경우(메시지는 영어 한 줄, `load: refused — <이유>`):
   - `resolve(dir)`가 저장소의 `data/`(`<repo>/data`)이거나 그 안.
   - `env.LECTERN_DATA_DIR`·`env.LECTERN_LECTURES_DIR`가 있고, `dir`가 그것과 같거나 그 안이거나 그것을 포함.
   - `dir` 안에 `lectern.sqlite`가 있다(이미 쓰이는 데이터 디렉터리다).
   - `dir`가 있고 비어 있지 않다(`lost+found`와 `.`으로 시작하는 항목은 무시).
   - `dir`가 `/`, 홈 디렉터리(`os.homedir()`), 저장소 루트 자체.
   통과하면 디렉터리를 만들고(`recursive`) 절대 경로를 돌려준다.
2. `lib/audio.ts`
   ```ts
   export interface SynthAudio { path: string; bytes: number; seconds: number; format: "wav" }
   /** 16 kHz mono 16-bit WAV of a tone plus noise. ffmpeg when present, a streamed TypeScript writer otherwise. */
   export async function synthAudio(dir: string, name: string, seconds: number, seed: number): Promise<SynthAudio>
   export function wavBytes(seconds: number, sampleRate?: number): number     // 44 + seconds * sampleRate * 2
   ```
   - ffmpeg가 있으면: `ffmpeg -v error -y -f lavfi -i "sine=frequency=<300+seed*37>:sample_rate=16000:duration=<s>" -f lavfi -i "anoisesrc=color=pink:sample_rate=16000:duration=<s>:amplitude=0.05:seed=<seed>" -filter_complex amix=inputs=2:duration=first -ac 1 -c:a pcm_s16le <path>`(`Bun.spawn`, 인자 배열. 셸 문자열을 만들지 않는다).
   - 없으면: 헤더 44바이트를 쓰고 1초(32,000바이트)씩 사인파를 `Bun.file(path).writer()`로 흘려 쓴다. 3시간(약 345 MB)도 메모리에 올리지 않는다.
   - `seed`가 다르면 내용이 달라야 한다(서버가 같은 오디오를 sha256으로 중복 처리하기 때문이다. 같으면 N건이 1건이 된다).
   - WAV를 쓰는 이유: 10분이 약 19 MB라 8 MiB 파트 3개가 된다(파트 경로를 실제로 탄다).
3. `lib/server.ts`
   ```ts
   export interface Sandbox {
     baseUrl: string;
     mode: "e2e" | "plain";
     processing: "on" | "unavailable" | "off";
     dataDir: string | null;                 // null in e2e mode (start.ts owns its temp dir)
     maxRssBytes(): number;
     alive(): boolean;
     stop(): Promise<void>;
   }
   export async function startSandbox(options: { processing: boolean; dataRoot?: string; port?: number }): Promise<Sandbox>
   ```
   - 포트: 주어지지 않으면 `Bun.serve({ port: 0 })`로 빈 포트를 얻고 바로 닫아 그 번호를 쓴다.
   - `processing: true`(→ `mode: "e2e"`): `Bun.spawn(["bun", "apps/web/e2e/server/start.ts", "--port", String(port)], { cwd: <repo>, env: { ...process.env }, stdout: "ignore", stderr: "inherit" })`. 이 서버는 스스로 임시 디렉터리를 만들고 끝날 때 지운다(`TMPDIR`을 따른다). `/api/health`가 200이 될 때까지 최대 60초 기다린다. 그다음 `POST /__e2e/pipeline` `{"mode":"v2"}`: 200이면 `processing: "on"`, 404면 `"unavailable"`(작업이 돌지 않는다. 업로드만 잰다).
   - `processing: false`(→ `mode: "plain"`): `dataRoot`(없으면 `mkdtemp`)를 `assertSandboxDir`로 확인하고, 그 아래 `data/`, `lectures/`, `home/`을 만든 뒤 `Bun.spawn(["bun", "apps/server/src/index.ts"], { env })`. `env`는 `start.ts`의 샌드박스 묶음과 같다: `LECTERN_DATA_DIR`, `LECTERN_LECTURES_DIR`, `HOME`, `LECTERN_RESEND_CREDENTIALS_FILE=<root>/no-credentials.json`, `PORT`, `LECTERN_BASE_URL=http://127.0.0.1:<port>`, `LECTERN_OWNER_EMAIL`·`LECTERN_OWNER_PASSWORD`·`LECTERN_OWNER_NAME`(`accounts.ts`의 값), `LECTERN_WORKER_MODE=external`(작업이 돌지 않는다 → AI 호출이 없다), `LECTERN_LOG_REQUESTS=0`, 그리고 `PATH`. **부모의 환경을 통째로 넘기지 않는다**(`GEMINI_API_KEY`, `RESEND_API_KEY`, `LECTERN_DEPLOY_TOKEN`, `LECTERN_OWNER_API_TOKEN`이 넘어가면 안 된다). `processing: "off"`.
   - 메모리: 1초마다 `ps -o rss= -p <pid>`(KiB)를 읽어 최댓값을 기억한다. `ps`가 실패하면 0으로 두고 계속한다.
   - `stop()`: `SIGTERM` → 최대 10초 기다림 → 안 끝나면 `SIGKILL`. `plain` 모드에서 `dataRoot`를 스크립트가 만들었으면(`mkdtemp`) 지운다. 사용자가 준 `dataRoot`는 지우지 않는다.
   - 스크립트가 예외로 끝나도 서버가 남지 않게 `process.on("exit")`와 `SIGINT`·`SIGTERM`에서 `stop`을 부른다.
4. `lib/client.ts`
   ```ts
   export interface Session { baseUrl: string; token: string; workspaceId: string }
   export async function signIn(baseUrl: string): Promise<Session>                 // POST /api/auth/login -> user.apiToken, GET /api/v2/me -> personal_workspace_id
   export interface UploadOutcome { ok: boolean; recordingId: string | null; bytes: number; parts: number; uploadMs: number; status: number | null; error: string | null }
   export async function uploadFile(session: Session, path: string, key: string): Promise<UploadOutcome>
   export async function waitForRecording(session: Session, recordingId: string, timeoutMs: number): Promise<{ status: string; ms: number }>
   export function partPlan(bytes: number, partSize: number): Array<{ part: number; offset: number; length: number }>
   ```
   - `uploadFile`: `POST /api/v2/uploads`(`Idempotency-Key: <key>`, `X-Lectern-Token`, `X-Client: load-test`, 본문 `{ workspace_id, files: [{ kind: "audio", filename, mime: "audio/wav", bytes }] }`) → 응답의 `part_size`와 `files[0].first_part`·`part_count`로 `partPlan` → 각 파트를 `Bun.file(path).slice(offset, offset + length)`를 본문으로 `PUT`(순서대로) → `POST …/complete`. 실패하면 던지지 않고 `ok: false`에 상태 코드와 `error.message`를 담는다(네트워크 오류는 `status: null`).
   - `waitForRecording`: `GET /api/v2/recordings/<id>`를 2초마다 읽어 `status`가 `ready`·`partial`·`failed`가 되면 끝. 시간이 넘으면 `{ status: "timeout" }`.
5. `lib/summary.ts`
   ```ts
   export interface LoadSummary {
     scenario: "uploads" | "long-recording" | "disk-full";
     started_at: string; duration_ms: number;
     host: { platform: string; arch: string; cpus: number; total_mem_bytes: number };
     server: { mode: string; processing: string; max_rss_bytes: number; alive_at_end: boolean };
     uploads: UploadOutcome[];
     processing: Array<{ recording_id: string; status: string; ms: number }>;
     failures: string[];
     ok: boolean;
     notes: string[];
   }
   export function percentile(values: number[], p: number): number          // nearest-rank; [] -> 0
   export function parseArgs(argv: string[], spec: Record<string, { default: string | number | boolean }>): Record<string, string | number | boolean>
   export function finish(summary: LoadSummary, outPath?: string): never    // prints JSON to stdout, writes outPath when given, exits 0 when ok else 1
   ```
   `parseArgs`: `--name value`와 `--flag`. 모르는 인자, 숫자 자리에 숫자가 아닌 값이면 사용법을 stderr에 내고 종료 코드 2.
6. `uploads.ts` — 인자 `--n 3`, `--minutes 10`, `--timeout-min 30`, `--no-processing`, `--out <file>`
   1. 임시 디렉터리에 오디오 N개(`seed` 1…N)를 만든다.
   2. `startSandbox({ processing: !noProcessing })` → `signIn`.
   3. N개를 **동시에** `uploadFile`(`Promise.all`. 키는 `load-<시작 시각>-<i>`).
   4. `processing === "on"`이면 성공한 것마다 `waitForRecording`(동시에).
   5. `ok` = 업로드 실패 0 **그리고** 서버가 끝까지 살아 있음 **그리고** (`processing`이 `on`이면) `timeout`·`failed` 0. `processing`이 `unavailable`이면 `notes`에 `processing was not run: the e2e server has no /__e2e/pipeline (P1-16)`.
   6. 오디오와 서버를 정리하고 `finish`.
7. `long-recording.ts` — 인자 `--hours 3`, `--timeout-min 120`, `--no-processing`, `--out`. `uploads.ts`와 같되 파일 하나, 길이 `hours × 3600`초. 요약의 `notes`에 파일 크기와 파트 수를 적는다.
8. `disk-full.ts` — 인자 `--volume <dir>`(필수), `--out`
   - `--volume`은 **작은 전용 볼륨의 마운트 지점**이어야 한다. `assertSandboxDir`에 더해 `statfsSync(volume)`의 전체 크기가 1 GiB를 넘으면 거절한다(`load: refused — the volume is larger than 1 GiB; use a small dedicated volume`). 볼륨을 만드는 것은 사용자(또는 테스트를 돌리는 사람)다. 만드는 법은 README와 런북에 적는다(macOS: `hdiutil create -size 200m -fs HFS+ -volname lectern-load <파일>.dmg` → `hdiutil attach <파일>.dmg -mountpoint <dir>`. Linux: `sudo mount -t tmpfs -o size=200m tmpfs <dir>` — sudo가 필요하므로 스크립트가 하지 않는다).
   - 순서: `startSandbox({ processing: false, dataRoot: volume })` → 2분짜리(약 3.8 MB) 오디오를 내용이 다르게 계속 올린다. 업로드가 실패하거나 60건이 되면 멈춘다.
   - 실패가 난 뒤 기록하는 것(전부 `notes`와 `failures`에):
     - 실패한 요청의 단계(`create`/`part`/`complete`)와 상태 코드
     - `GET /api/health`가 여전히 200인가(`alive_at_end`와 별도로 `notes`에)
     - 성공으로 응답한 업로드 수 == `GET /api/v2/recordings`의 건수인가(**성공이라고 답해 놓고 잃은 녹음이 없는지**)
     - 가장 최근 업로드 세션을 `DELETE /api/v2/uploads/<id>`로 버린 뒤, 1초짜리 오디오 업로드가 되는가(여유가 생기면 다시 받는지)
   - `ok` = 서버가 살아 있음 **그리고** 건수가 일치함. 디스크가 차서 업로드가 거절된 것 자체는 실패가 아니다. 60건을 다 받도록 디스크가 차지 않았으면 `ok: false`, `failures: ["the volume never filled up"]`.
   - 볼륨의 내용은 지우지 않는다(사용자가 볼륨을 통째로 버린다).
9. `README.md`(40줄 이내): 세 스크립트의 한 줄 설명, 명령 예(`bun scripts/load/uploads.ts --n 3 --minutes 10`), 요약 JSON 필드 표, 안전 규칙(실제 데이터 디렉터리 거절, 실제 AI 호출 없음), 작은 볼륨 만드는 법.
10. `docs/runbooks/load-test.md` — 다른 런북과 같은 문체. 절:
    1. 언제 돌리나(큰 변경 뒤, 호스트 교체 뒤) / 운영 서버에 주는 영향(CPU·디스크를 같이 쓴다. 한가한 시간에)
    2. 준비: 운영 서비스는 그대로 둔다. 스크립트는 다른 포트의 별도 서버를 띄운다. `TMPDIR`을 데이터 디스크의 빈 디렉터리로(예: 3시간 WAV는 345 MB, 처리 중간 산출물까지 약 1.5 GB 여유). 운영 환경 파일을 `source` 하지 않는다
    3. 실행: 세 명령과 권장 인자(Pi: `--n 3 --minutes 30`, `--hours 3`, 디스크 시험은 tmpfs 200 MB)
    4. 결과 읽기: `server.max_rss_bytes`(Pi 메모리의 50%를 넘으면 조사), 업로드 시간 p95, 처리 시간, `failures`
    5. 치우기: tmpfs `umount`, `TMPDIR` 삭제
    6. 기록: 요약 JSON을 어디에 두는지(저장소에 올리지 않는다. `STATUS.md`의 "실측 필요" 항목에 날짜와 수치만 적는다)
    런북의 명령에 실제 호스트 이름·사용자 이름·경로의 개인 값을 넣지 않는다(환경 변수나 `<…>` 설명으로).
11. 로컬에서 한 번 실제로 돌린다(수용 기준): `bun scripts/load/uploads.ts --n 3 --minutes 10 --out <scratch>/uploads.json`. 요약을 결과 보고에 붙인다. `long-recording.ts`와 `disk-full.ts`는 `--hours 0.05`와 작은 볼륨(macOS면 `hdiutil`)으로 한 번씩 돌려 본다. 볼륨을 만들 수 없는 환경이면 `disk-full.ts`는 "거절 경로만 확인"이라고 보고한다.

## 6. 테스트

`scripts/load/load.test.ts`(`bun test`가 줍는다. 서버를 띄우지 않는 순수 테스트만)

| 테스트 이름 | 준비 | 기대 |
|---|---|---|
| refuses the repository data dir | `<repo>/data`, `<repo>/data/x` | 던진다 |
| refuses the configured data dir | `env.LECTERN_DATA_DIR = /a/b`, dir `/a/b`, `/a/b/c`, `/a` | 셋 다 던진다 |
| refuses a dir with a database | 임시 디렉터리에 `lectern.sqlite` | 던진다 |
| refuses a non-empty dir | 임시 디렉터리에 파일 하나 | 던진다. `.DS_Store`만 있으면 통과 |
| refuses home and root | `/`, `os.homedir()` | 던진다 |
| accepts a fresh temp dir | `mkdtemp` 아래 새 이름 | 절대 경로를 돌려주고 디렉터리가 생긴다 |
| part plan covers the file | 20,000,000바이트, 파트 8 MiB | 3개, 길이 합 == 파일 크기, 마지막이 짧다 |
| part plan for a tiny file | 10바이트 | 1개 |
| wav writer without ffmpeg | TypeScript 경로로 2초 | 크기 == `wavBytes(2)`, 헤더 `RIFF`…`WAVE`, seed가 다르면 내용이 다르다 |
| percentile | `[1..100]`, p95 | 95. 빈 배열 0 |
| parseArgs | `--n 5 --no-processing` | `{ n: 5, "no-processing": true, … }`. 모르는 인자는 종료 코드 2(함수를 `process.exit` 대신 던지는 내부 함수로 나눠 시험한다) |
| summary ok rules | 업로드 실패 1건 | `ok === false` |

## 7. 검증 명령

```bash
bun test scripts/load
```
```bash
bash scripts/pipeline/gate.sh unit
```
```bash
bun scripts/load/uploads.ts --n 3 --minutes 10
```
마지막 명령은 종료 코드 0과 JSON 요약(`"ok": true`)이 나와야 한다. 그리고
```bash
LECTERN_DATA_DIR="$PWD/data" bun scripts/load/disk-full.ts --volume "$PWD/data"; echo "exit=$?"
```
는 `load: refused`와 0이 아닌 종료 코드가 나와야 한다(아무것도 만들지 않는다).

## 8. 하지 않는 것

- 서버·웹·e2e 코드 수정(`start.ts`도 읽기만 한다).
- 실제 Gemini 호출, 실제 메일.
- Pi에서의 실행(사용자 몫. STATUS "실측 필요").
- CI에 부하 시험 넣기.
- 디스크가 찼을 때의 서버 동작을 고치는 것(이 작업은 관찰해 기록한다. 고칠 것이 보이면 STATUS에 적는다).
- sudo가 필요한 명령을 스크립트가 실행하는 것.

## 10. 명세 작성자 메모

- 처리 단계(전사·노트)를 가짜 AI로 돌리는 서버는 `apps/web/e2e/server/start.ts`뿐이다(P1-16이 가짜 Gemini와 작업 러너를 넣는다). 그래서 그것을 그대로 띄우고, P1-16을 의존에 넣었다(CATALOG의 원래 의존은 P1-12뿐이었다).
- `start.ts`의 가짜 전사는 청크마다 같은 세 문장을 준다. 3시간 처리에서 보는 것은 ffmpeg 분할·청크 수·메모리이지 전사 품질이 아니다.
- 서버에는 "디스크가 부족하면 업로드를 거절한다"는 규칙이 없다(`diskStats().low`는 보고용이다). `disk-full.ts`의 관찰 결과에 따라 그런 규칙이 필요하면 새 작업으로 올린다(STATUS에 적었다).
- 루트 `package.json`에 스크립트 이름을 더하지 않았다(소유 밖이다). 필요하면 P7-05에서 더한다.
