# 명세 작성 규칙 (SPEC-WRITER)

`wp/<ID>.md`를 새로 쓰거나 다시 쓰는 세션이 따르는 규칙이다. 명세는 **코드가 아니다.** 아주 작은 모델의 워커가 다른 문맥 없이 읽고 그대로 구현할 수 있어야 한다.

언제 쓰나
- 어떤 WP의 `wp/<ID>.md`가 없을 때(`bun run pipeline start`가 거절한다).
- 워커가 "명세가 실제 코드와 맞지 않는다"로 `BLOCKED`를 보고했고, 원인이 설계가 아니라 **명세가 낡은 것**일 때(앞선 WP가 만든 파일 이름·시그니처가 명세와 다르다 등). 설계 자체가 틀렸으면 명세를 고치지 말고 사용자에게 보고한다.

명세 작성은 워커보다 좋은 모델로 한다. 작은 모델밖에 없으면 명세를 새로 쓰지 말고 그 WP를 `block`한 채 사용자에게 넘긴다.

## 읽는 순서

1. `AGENTS.md`
2. [WORKER.md](WORKER.md)
3. [CONTRACTS.md](CONTRACTS.md) 전부
4. [CATALOG.md](CATALOG.md)에서 그 WP의 항목(이웃 WP는 경계를 알 만큼만)
5. [RECIPES.md](RECIPES.md)
6. [`wp/_TEMPLATE.md`](wp/_TEMPLATE.md)
7. [`pipeline.json`](pipeline.json)에서 그 WP의 등급·게이트·의존·소유
8. 그 WP가 건드리는 **실제 코드**와 그 옆의 테스트. 의존 WP가 이미 합쳐졌으면 그 WP가 만든 코드를 읽는다.

## 규칙

1. CONTRACTS와 CATALOG가 원본이다. 거기서 정한 이름, 경로, 시그니처, 테이블, 플래그, 결정을 바꾸지 않는다. 불가능하거나 실제 코드와 부딪히면 계약대로 쓰고, 부딪히는 점을 10절(명세 작성자 메모)에 적는다.
2. 실제 코드에 근거한다. 기존 코드는 `경로` + 심볼 이름으로 가리킨다(줄 번호 금지). 가리키기 전에 `git grep`으로 있는지 확인한다. 아직 없는 모듈은 "`<ID>`가 만든다"와 계약의 경로·시그니처를 적는다.
3. 머리말의 등급·게이트·의존·소유는 `pipeline.json`과 글자 그대로 같아야 한다.
4. 3절(사전 점검)에는 명세가 기대는 심볼이 있음을 보이는 실제 `git grep` 명령을 넣는다.
5. 5절(단계)은 작고 순서가 있다. 한 단계는 파일 하나이고, 무엇을 더하거나 바꾸는지 정확히 적는다. 뼈대(내보내는 이름, 시그니처, zod 모양, 컬럼 목록, JSON 내용)는 주되 구현 전체를 적지 않는다. 계약이 정확한 내용을 준 것(표, JSON, 기대값)은 명세에 전부 옮겨 적는다. 워커가 다른 문서를 열지 않아도 되게 한다.
6. 6절(테스트)은 테스트 이름, 구체적인 준비, 구체적인 기대값(문자열, 숫자, 상태 코드)의 표다. 카탈로그 항목의 수용 기준을 전부 덮는다. 테스트는 가짜만 쓴다(스크립트 공급자, 가짜 `fetch`). 본뜰 기존 테스트 파일을 적는다.
7. 7절은 정확한 명령이다: `bun test <파일>`, `bash scripts/pipeline/gate.sh <단계>`(Apple·Android는 PIPELINE.md의 게이트 표).
8. 8절에는 이 WP가 하지 않는 일을, 그것을 하는 WP의 id와 함께 적는다.
9. 사용자에게 보이는 문구(화면 글자, 오류 메시지, 메일 제목과 본문)는 명세에 한국어로 전부 적는다. 워커가 문구를 지어내지 않게 한다.
10. 소유 경로 안에서 끝나야 한다. 밖의 파일을 고쳐야 끝낼 수 있으면 10절에 적는다.
11. 한국어 산문(짧은 명령문), 식별자·코드·코드 주석은 영어. 명세 하나는 170줄 안팎이다.
12. 확인하지 못한 것은 추측으로 채우지 않고 "확인 필요: …"로 적는다.

## 끝나면

- `bun run pipeline check`가 그 WP의 명세 누락을 더 보고하지 않는지 본다.
- 10절에 적은 충돌을 한 줄씩 보고한다. 설계와 부딪히는 것은 `STATUS.md`의 "넘겨받은 요청" 표에도 옮긴다.
- 명세만 커밋한다: `docs(pipeline): <ID> 명세`.
