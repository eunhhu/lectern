# ADR-0004: 데이터 모델은 첫날부터 워크스페이스 단위

- 상태: 채택 (ROADMAP D5)
- 날짜: 2026-10-19
- 관련: [ROADMAP.md D5](../v2/ROADMAP.md#결정-필요-사항), [ARCHITECTURE.md §5](../v2/ARCHITECTURE.md#5-도메인--데이터-모델-v2), [§10](../v2/ARCHITECTURE.md#10-계정인증권한쿼터공유)

## 맥락 (Context)

현재 데이터는 사용자 단위다. `lectures.owner_id`가 소유자를 가리키고, 권한 검사는 "본인 것인가, 관리자인가" 두 가지뿐이다. 공유는 강의마다 공개 토큰(`/s/:token`) 하나로 한다.

v2는 회의, 세미나, 인터뷰까지 다룬다. 이런 녹음은 여러 사람이 함께 보고 고치는 경우가 많고, 팀 워크스페이스(초대, 역할, 공유)가 P5 범위에 있다. 팀 기능을 나중에 붙이면서 소유 단위를 사용자에서 워크스페이스로 바꾸면 다음 비용이 든다.

- 모든 테이블에 컬럼을 추가하고 백필하는 마이그레이션을 다시 해야 한다.
- 권한 검사, 쿼리, 색인, 캐시 키, SSE 채널을 전부 다시 고쳐야 한다.
- 그 사이에 API 계약이 깨져 네이티브 클라이언트도 다시 맞춰야 한다.

선택지
1. 사용자 단위로 만들고 팀 기능 때 바꾸기: 지금은 단순하지만 위 비용을 P5에서 한 번에 치른다.
2. **워크스페이스 단위로 만들고, 사용자마다 개인 워크스페이스를 자동 생성**: 컬럼과 권한 검사 위치를 처음부터 맞춘다. 팀 UI는 나중에 붙인다.

## 결정 (Decision)

2번을 택한다.

- **모든 v2 테이블에 `workspace_id`를 둔다**(`recording`, `asset`, `folder`, `tag`, `document`, `job`, `share_link`, `usage_ledger`, `audit_log` 등).
- `workspace(kind = personal | team)`와 `membership(role = owner | admin | member | viewer)`을 둔다. 가입하면 개인 워크스페이스가 자동으로 만들어진다.
- 시스템 역할(`users.role`: 운영자)과 워크스페이스 역할은 분리한다.
- 권한은 미들웨어에서 멤버십을 확인하고, 리소스 단위 정책 함수(`can(user, action, resource)`) 하나에 모은다. 역할 × 행동 × 리소스 표 형태의 테스트로 검증한다.
- 검색(FTS), SSE 이벤트, 쿼터, 블롭 서빙은 모두 워크스페이스로 범위를 제한한다.
- 기존 `lectures`는 각 소유자의 개인 워크스페이스로 옮긴다([ARCHITECTURE.md §5.3](../v2/ARCHITECTURE.md#53-기존-데이터-이전-lectures--v2)).
- 팀 UI(초대, 역할 변경, 공유 설정)는 P5에서 만든다. 그 전까지 사용자 눈에 보이는 워크스페이스는 개인 하나뿐이다.

## 결과 (Consequences)

- 좋아지는 것
  - P5 팀 기능이 스키마 변경 없이 UI와 정책 추가로 끝난다.
  - 데이터 경계가 하나(워크스페이스)라 "다른 사람 데이터가 보인다" 유형의 버그를 한곳에서 막는다.
  - 쿼터와 사용량을 워크스페이스 단위로 청구할 수 있다(결제는 보류).
- 감수하는 것
  - P2부터 모든 쿼리에 `workspace_id` 조건이 붙는다. 빠뜨리면 데이터가 샌다. 리포지토리 계층에서 강제하고 정책 테스트로 막는다.
  - 개인 워크스페이스만 쓰는 동안에는 한 단계 간접 참조가 군더더기처럼 보인다.
  - v1 어댑터(`/api/lectures`)는 사용자 → 개인 워크스페이스 변환을 해야 한다.
- 다시 검토할 신호
  - 한 녹음을 여러 워크스페이스에 동시에 두어야 한다는 요구가 생길 때(지금 모델은 녹음 하나가 워크스페이스 하나에 속한다)
