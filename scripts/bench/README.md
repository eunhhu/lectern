# 검색 성능 측정

`search.ts`는 합성 녹음을 임시 SQLite 파일에 색인하고, `GET /search`가 쓰는 검색(`searchIndex`, BM25 + 벡터 RRF)의 지연 시간을 잰다(P3-10, D-P3-5).

- 녹음은 `synth.ts`가 시드로 만든다. 녹음 하나는 세그먼트 300개이고, 세그먼트 하나는 일상 낱말 200개 목록에서 뽑은 낱말 12~20개다. 실제 강의나 사람의 데이터는 없다.
- 임베더는 결정적 가짜(`FakeEmbedder`, 768차원)다. 네트워크를 쓰지 않는다.
- DB는 OS 임시 디렉터리의 `lectern-bench-*`에 만들고 끝나면 지운다. `LECTERN_DATA_DIR`와 저장소의 `data/`는 읽지도 쓰지도 않는다.

## 실행

```bash
bun scripts/bench/search.ts --recordings 200
```

```bash
bun scripts/bench/search.ts --recordings 1000 --max-p95-ms 200
```

| 인자 | 기본값 | 뜻 |
|---|---|---|
| `--recordings <n>` | 1000 | 색인할 합성 녹음 수 |
| `--queries <n>` | 200 | 잴 질의 수(앞의 예열 20개는 따로 버린다) |
| `--max-p95-ms <n>` | 없음 | 주면 p95가 이 값을 넘을 때 종료 코드 1 |
| `--seed <n>` | 1 | 녹음과 질의를 만드는 시드 |

## 수치 읽는 법

stdout에 JSON 한 줄이 나온다. 진행 상황(100건마다)은 stderr로 간다.

```json
{"recordings":1000,"chunks":21660,"queries":200,"p50_ms":42.98,"p95_ms":53.06,"max_ms":66.01}
```

- 위 수치는 Apple M3 개발 기계에서 시드 1로 한 번 돌린 값이다(색인 포함 약 37초).
- `chunks`: 색인된 조각 수. 전사 창 하나가 조각 하나다.
- `p50_ms`, `p95_ms`: 가장 가까운 순위 방식의 백분위. 질의 하나는 질의 임베딩(가짜라 거의 0), BM25, 벡터 검색, RRF, 스니펫까지다. HTTP와 권한 범위 계산은 들어가지 않는다.
- `max_ms`: 가장 느린 질의.

## 주의

- 로드맵의 기준(검색 p95 200 ms)은 Raspberry Pi 기준이다. 개발 기계의 수치는 참고값이다. Pi에서 돌린 결과는 `docs/v2/pipeline/STATUS.md`의 "실측 필요"에 적는다.
- 실제 임베딩 호출의 지연(질의마다 한 번, 캐시에 없을 때)은 들어가지 않는다. 운영에서는 그만큼 더 걸린다.
- CI에는 넣지 않았다(P7-03이 시간 예산을 정한다).
